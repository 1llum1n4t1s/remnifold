# R2 publication and trust

- CI の検証・ビルドコマンドは、Node.js や JavaScript パッケージマネージャーを決して呼び出さない（PATH ガード）。SHA 固定でホワイトリスト化された Actions（`dev/src/ci.rs`）は、ランナー同梱の Node で動かしてよいが、`publish-r2`、シークレットを使うステップ、`release/*` の実行では決して動かさない。この節の残りは strict 公開について述べるもので、strict 公開は 1.0.32 で終了し、既存のリリースのためにだけ残る。アーカイブは、ネイティブランナー上の `release/*` の実行だけが、ビルド・検証・非公開ステージングを行う（手作業で作ったアーカイブやローカルの入力から作ったアーカイブは不可）。すべての CI ジョブが成功した後に、公開者だけが、公開の `remnifold-updates`（`https://remnifold-updates.kagayoi.com`）へ不変のオブジェクトを書き込み、ステータスを作成し、`releases/<version>/index.json` を条件付きで更新する。`velopack/` プレフィックスへは `release-velopack.yml` だけが書き込み（[Setup installer (Velopack)](setup-installer-velopack.md) を参照）、`releases/` には決して触れない。
- 各 `native-package` の区間は、それぞれのネイティブランナー上（ターゲットごとの `runs-on`、ホストは `CI_TARGET` に対して検証する）で、prepare、package、verify、updater-test、ステージングを実行し、`publish-r2` は `ubuntu-latest` で実行する状態を保つ。型チェックとテストは、`server-contracts`（`ubuntu-24.04`）、`windows-native-contracts`、`windows-client-contracts` で並列に実行する（Environment なし、読み取り専用、ジョブレベルの `if` なしなので、`main` への push を含むすべてのイベントで動く。`server-test` は 48 ケースのバッチを並列に実行しつつ、workerd は直列に起動する）。`publish-r2` がすべてのジョブを必要とするため、公開は待機する。実行・試行ごとに範囲を分けた出力先と一時ディレクトリを保つ。ただし、`Swatinem/rust-cache` 用の固定の `$GITHUB_WORKSPACE/target` は例外とする（`main` でのみ保存する）。
- GitHub Environments が認証情報の境界である。`r2-staging` は `release/*` だけを選択する（`main` への push はシークレットなしの `validation` で動き、ステージングは決してしない）。`r2-release` は、strict 公開のときは `release/*` を選択しており、現在は `release-velopack.yml` を始めるバージョンタグ `v*.*.*` を選択する。選択ブランチのポリシー（`protected_branches: false`、`custom_branch_policies: true`）を使い、`ref_protected` は使わない。これにより PR による配布アクセスは拒否される（オーナー／書き込み権限は引き続き信頼する）。ステージング用の認証情報は非公開のものだけにし、公開用バケットの権限は最小限に保つ。ステータスを書き込めるのは公開者だけとする。
- コミットステータスの URL は、GitHub が公開を生成したことの証明にならない。リポジトリ／ワークフロー／コミット／push／リリースブランチ／実行試行の正確な識別と、最新の成功した CI の唯一の成功した `publish-r2` ジョブを要求する。そのジョブの上限付き生ログには、マニフェストの記録がちょうど 1 件と、一致する一意な V2 アセットの記録が 4 件なければならない（リリース schema 2。過去の schema 1 では V1 の記録 5 件すべてが必要）。インストールの前に、schema の混在、部分的、重複、不一致、未知のターゲット、欠落したウィットネスを拒否する。schema 2 のレシートは、公開とウィットネスの実行識別を別々に保つ。
- 公開オブジェクトのキーとハッシュは不変である。繰り返しの公開では、ログと完全な公開バイト列から、受理済みの以前のインデックスを証明しなければならない。暫定的な失敗・キャンセル・タイムアウトした公開からの回復では、ETag の CAS の前に、候補のログと以前のオブジェクトルート全体を検証しなければならず、成功して受理済みのインデックスを決して上書きしない。競合する公開者と中断された書き込みを、隔離したフィクスチャでテストする。
- ウィットネスのログが欠落している場合は、安全側に倒して失敗する。既存のレシートがあれば、保持された R2/CI のオブジェクトがなくても `--verify-only` は許されるが、GitHub のリリース／ソースのメタデータは引き続き必要である。設定のない過去のリリースに対する GHA/schema-1 の互換性を保つ。存在する R2 設定が不正な場合や、R2 の公開が無効な場合は、従来のアーティファクトへ決してダウングレードしない。

Unix のアーカイブは、同じ `native-package` の区間が、常にクリーンな Git ソースに対するコミットモードでビルドする。チェックアウトモードのパッケージは決してアップロードしない。4 つの区間は、プルリクエスト、手動ディスパッチ、`release/*` への push、バージョンタグの push のときだけ動く（`main` への push では高速なコントラクトジョブだけが動き、それを `scripts/velopack/wait-main-ci.sh` のリリースゲートが判定する。タグの実行は並行するチェックで、ゲートはそれを待たない）。PR、ディスパッチ、タグの実行は、シークレットなしの `validation` Environment を使い、ステージングは決してしない。Unix の実行時カバレッジは、パッケージの検証と updater-test に限られる。
