# Local app integration

アプリは管理者権限なしでユーザーごとにインストールされます。場所は、Windows では `%LOCALAPPDATA%\Programs\Remnifold`、macOS では `~/Library/Application Support/Remnifold/app`、Linux では `$XDG_DATA_HOME/remnifold`、または `<REMNIFOLD_HOME>/app` です。検証済みの各バージョンは一度だけ `versions/<version>` に展開され、内容の異なる既存のバージョンフォルダーが置き換えられることはありません。`bin/remnifold(.exe)` はすべての登録が参照する固定の実行ファイルで、`receipts/` はオフライン検証用のレシートを保持し、`current.json` はインストール済みのバージョンを指します。置き換えでは、検証済みの新しいファイルを書き込み、名前を変更して所定の位置に入れます。Windows では実行中の実行ファイルを上書きできませんが名前の変更はできるため、古いファイルを先に脇へ移し、使われなくなってから削除し、結果は `restartRequired` を報告します。接続ファイルは `remnifold.json`、`kagayoi-memory.json`、`supermemory.json` の順に、まず設定フォルダーで、次に以前の Codex ホームで読み込まれます。セットアップは現行のファイルを書き込み、以前のファイルは残します。環境変数による上書きとユーザー向けのアップグレード手順は [README.md](../readme/upgrading-from-1-x-names.md) に記載しています。

`connect claude-code` は固定の実行ファイルを登録します。MCP サーバーは公式の `claude mcp add --scope user` を通して登録し（CLI が `PATH` にない場合はそのコマンドを表示します）、`PreToolUse`、`SessionStart`、`UserPromptSubmit` と非同期の `Stop` の各フックは、パッケージのマッチャー、タイムアウト、ステータスメッセージのまま、Claude Code の `settings.json` へマージします。自動想起が off のとき（`recallMode` はフックが読むのと同じ方法、つまり同じフォールバック設定に対する `read_settings` で読むため、設定がなければ `off` と数えます）、`SessionStart` と `UserPromptSubmit` は登録されず、これらに対する Remnifold の既存のエントリは削除されます。`Stop` と `PreToolUse` は常に残ります。`PreToolUse` フックは、`sessionId` が `"current"` である `search_memory` の呼び出しも書き換えます。`updatedInput`（入力全体を置き換える）を返し、ペイロードの `session_id` を設定して、他の引数は変更しません。マッチャーは `^mcp__remnifold__|^mcp__toolport__toolport_call_tool$`（ステータスメッセージは "Checking tool access..."）で、直接登録した `mcp__remnifold__*` に加えて Toolport ゲートウェイの `mcp__toolport__toolport_call_tool` も対象にします。後者は `tool_input.name` が `<registry 上の Remnifold サーバーの id を Toolport のツール名の前置きに変換したもの（`[A-Za-z0-9_]` 以外を `_` に置き換え。例: `etw-mcp` は `etw_mcp`）>__<読み取り専用の7ツール>` に完全一致するとき（最後の `__` で分割して推測はしない）だけ、同じ読み取り許可と `sessionId: "current"` の置き換えを行い、`updatedInput` は `tool_input` 全体の複製のまま `arguments` だけを置き換えます。読み取り専用ツール名の判定を先に行い、一致したときだけ registry を読みます（プロセス環境変数と既定パスだけで解決し、`~/.claude.json` は読まず、サーバーの有効・無効やプロファイルも見ません）。別サーバーの同名ツール、書き込みツール、registry を読めない場合は `{}` を返して許可しません。ゲートウェイのサーバー名が `toolport` でない場合と、`toolport_run_script` 内の呼び出しは対象外なので、セッション ID を明示する必要があります。実装は `native/src/hooks.rs` と `native/src/toolport.rs` です（後者は Edictora の `crates/edictora/src/install/toolport.rs` を正本とするバイト同一の複製で、ここでは編集しません）。マージは、そのイベントについて Remnifold を実行するコマンドのエントリ（以前のランチャーを含む）だけを置き換え、他の設定はすべて保持し、不正な形式のファイルは拒否し、一度だけのバックアップを保持します。Claude Code は Windows では Git Bash を通してフックを実行するため、コマンドはスラッシュ区切りの実行ファイルのパスを引用符で囲み、引用や展開に使われる文字を含むパスは拒否します。`connect <tool> --remove` はその逆の操作です。コマンドが Remnifold を実行するエントリだけ（`--executable` を付けた場合は、そのファイルを指すものだけ）を削除し、空になったイベントと `hooks` を取り除き、`claude mcp remove remnifold --scope user` または `codex mcp remove remnifold` を実行します。`connect codex` は、Codex にはプラグイン外でフックを登録する公式の方法がないため、`codex mcp add` を通して MCP サーバーだけを登録します。パッケージは引き続き `.codex-plugin/`、`.mcp.json`、`hooks/` の登録をソース資産として含みますが、これらはもはやインストールの経路ではありません。

`dev/` の Rust パッケージャーは、生成されたネイティブの MCP とフックの登録を含む、許可リスト化されたプラットフォームアーカイブを構築します。出力パスはリンクされた祖先がないか検査され、リポジトリ内の出力は `dist/` の下に置く必要があります。検証では、公開の前に、アーカイブを同じソースのチェックアウトおよび実際の実行ファイルと照合します。

Windows のパッケージは、4 つのフックすべてに `commandWindows` の上書きを加え、固定の Git for Windows シェルを使ってネイティブの実行ファイルを起動します。パッケージャーとパッケージ検証は、`native/src/hook_command.rs` にあるランチャー定義を共有します。外側のコマンドには、固定の 8 進数エンコードされたスクリプトだけが含まれます。Git Bash が環境から `PLUGIN_ROOT` を読み取って引用符で囲むため、プラグインのパスは外側のシェルによる展開に入らず、元の stdin も保たれます。これにより、プラグインのパスに含まれる Unicode とシェルのメタ文字に対応しつつ、ワークスペースや `PATH` によるシェル解決を避けます。通常の直接コマンドは、macOS/Linux と過去のパッケージ向けに残ります。アップデーターの検証は、上書きが一切ないか、完全で正確な Windows 用の一式があるかのどちらかを受け入れ、一部だけの一式や、他のターゲットでの上書きは拒否します。
