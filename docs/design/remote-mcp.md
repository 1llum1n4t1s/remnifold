# Remote MCP

ステートレスな Streamable HTTP のエンドポイントは `/mcp` である。既存の API キーを Bearer 資格情報として受け付けるほか、保護リソースと認可サーバーのディスカバリー、公開の動的クライアント登録、PKCE S256 を用いた認可コード、リフレッシュ、失効を通じて発行される、MCP 用スコープの OAuth アクセストークンも受け付ける。オーナーの同意には既存の API キーが必要である。OAuth トークンでは既存の REST API を認可できない。リモートのツールは、同じバックエンドを使って、既存のスペースを検索し、レコードを取得または保存する。保存済みのメモリを移動したり複製したりはしない。サーバーの指示は、クライアントに、検索し、必要に応じて詳細を開き、継続的な価値のある結果を保存するよう求めるが、ツールが呼ばれるかどうかはクライアントとモデルの挙動で決まる。Codex の stdio トランスポートとフックは別物であり、変更されない。

`server/src/mcp-oauth.ts` は、ディスカバリーと、移行 `0008_remote_mcp_oauth.sql` で永続化される OAuth 資格情報を担う。Worker のルーターは、`server/src/mcp.ts` のトランスポートアダプターを呼ぶ前に、資格情報とブラウザーのオリジンを確認する。アダプターはツールの引数を検証し、オーナーの API キーを使って既存の REST ルートを内部的に呼び出すため、それらの保存とミューテーションのルールが保たれる。そのため OAuth の同意は、クライアントごとに分離されたコレクションではなく、そのインストールのメモリへのアクセスを許可することになる。リモートの保存は、明示的な `projectId` による出所を受け付け、ローカルのワークスペースフォルダーを推測しない。リモートの統合も、Codex の stdio ツールがワークスペースルートへフォールバックするのとは異なり、明示的な `projectId` を必要とする。

リモートの保存は、Codex のキャプチャと同じシークレット伏せ字の実装を使い、さらに現在の OAuth 資格情報を取り除く。渡された冪等キーは、物理スペース、プロジェクト、伏せ字後の内容にスコープされるため、再試行は、別のプロジェクトのメモリを上書きすることなくレコードを再利用する。OAuth のアクセストークンは 1 時間で失効し、リフレッシュトークンはローテーションされて 30 日で失効する。リフレッシュトークンを再利用すると、そのトークンファミリーが失効し、オーナーの API キーを変更すると、発行済みの資格情報が無効になる。登録は、送信元 IP とオリジンごとに 1 時間あたり 10 リクエストまでに制限される。承認されていない登録は 24 時間で失効し、承認済みのクライアント識別は有効なままである。ブラウザーからの MCP リクエストには、サーバー自身のオリジン、または `MCP_ALLOWED_ORIGINS` にカンマ区切りで指定した完全一致のオリジンが必要であり、サーバー間のクライアントは通常 Origin ヘッダーを送らない。OAuth の同意は常に同一オリジンを必要とする。

認可フォームは、同意の POST の Origin を保つために `Referrer-Policy: same-origin` を使う。その CSP は `form-action 'self'` を保つ。Allow または Deny の後、サーバーは、スクリプトを含まない meta refresh と、完全に検証済みのコールバック URL へのフォールバックリンクを備えた、HTTP 200 の完了ドキュメントを返す。これにより、アプリケーション自身のリダイレクトチェーンの前にフォーム送信のナビゲーションが終わるため、Chromium がフォームの CSP を下流のアプリケーションホストに適用することはない。完了の応答は `no-store` と `no-referrer` を使い、同意の Cookie を消去し、フォームの本文やオーナーキーを転送しない。コールバック URL は、登録された識別、state、code を変えずに HTML エスケープされる。認可とトークン交換の際の完全一致のリダイレクト照合は引き続き必須で、null や外部の同意オリジンは引き続き拒否される。
