# Project consolidation

プロジェクトの統合は、ライフサイクルフックではなくサーバー側で実行される。空でない `metadata.sm_project_id` を持つ記録は、その来歴 ID でコンテナをまたいでグループ化され、それがない記録は物理コンテナでグループ化される。チェックポイントは常に `memories` に保存される。Worker は既存の15分ごとのベクトル照合のスケジュールを保ち、それらのグループを調べるために、18:00 UTC（03:00 JST）の別の日次 cron を使う。新しいプロジェクトが期限に達するのは、未統合の記録が20件以上ある場合か、最も古い保留中の記録から3日が経過した場合である。チェックポイントが成功した後は、3日の間隔はその成功から数える。開始されたが未完了の初回バックフィルは期限が来た状態のままで、それらのしきい値を再び満たさなくても再開できる。

プロジェクトで最初に期限が来たスケジュール実行は、前のチェックポイントをバッチ間で引き継ぎながら、最大40件の新しい記録ずつの連続したバッチで、過去のバックログ全体を処理しきる。繰り返しのスケジュール作業は、1回の起動につき、期限が来た最大25のプロジェクトそれぞれに1バッチを処理する。手動実行の契約は [commands.md](commands.md)。

移行 `0005_memory_consolidations.sql` は、統合の状態と正確なソースのメンバーシップを、ユーザーのメタデータとは別に記録する。公開されたチェックポイントは新しいメモリ行で、その永続化されたメタデータは、上限のあるソース ID のプレビューを含む。グローバルな索引のみの想起は、`sourceMemoryIds` を、正確なメンバーシップと最終的に返された候補との積集合として返し、合計の `sourceCount` を保持して、`sourceMemoryIdsTruncated: true` を設定する。これにより、ランキングのメタデータは、プロジェクトの履歴とは無関係に上限が保たれる。コンテナを明示した互換検索は、引き続き完全なメンバーシップを返す。ソースの行が統合によって削除されることはない。置き換えを公開すると、以前のチェックポイントに置き換え済みの印が付く。ソースの upsert、更新、再エンリッチメント、忘却、物理削除は、依存するチェックポイントを無効にするので、古い内容や忘却された内容が、それらを通じて見える状態のまま残ることはない。自動の想起は、まず索引、トピック、元の抜粋にまたがってクエリ語の一致を順位付けし、次に抜粋なしで索引/トピックの関連度で順位付けし、両者が等しい場合はアクティブなチェックポイントを優先する。最終的な選択に入ったチェックポイントだけが元の記録を抑止し、それも、チェックポイントがその元の記録に一致するクエリ語をカバーしている場合に限られる。チェックポイントから省かれた特定の詳細が、元の記録を表に出すことがある。手動の検索は元の記録を保持する。生成の失敗や、公開ガードの失敗では、置き換えは公開されず、保留中のソースも消費されない。以前のチェックポイントがアクティブのままなのは、それ自身のソースが有効な間だけである。

リクエストは、生成を始める前にプロジェクトのリースを取得しなければならない。公開は、リーストークン、新しいソースの現在のリビジョン、以前のチェックポイントのアクティブな状態とソースのリビジョンを検証するので、生成中の変更によって古い内容が公開されることはない。オプトアウトされた記録は、統合の対象と新しい入力から除外される。以前のチェックポイントと、その永続化された正確なソースも、生成の前と公開時に、想起可能のままでなければならない。移行 `0011_consolidation_recall_opt_out.sql` は、オプトアウトされたソースを含む過去のアクティブなチェックポイントを無効にし、元の記録とメンバーシップを保持して、きれいに再生成できるよう初回バックフィルをリセットする。忘却されたチェックポイントのベクトルは、既存の照合による掃除を使う。

公開されたチェックポイントは生成された記録である。ドキュメントの PATCH と custom-ID の upsert を直接行うと、その内容やメタデータを変更する前に 409 を返す。これは、ユーザーのメタデータではなく、永続化された統合のメンバーシップに対して検査される。代わりに、元のソースの記録を編集してチェックポイントを再生成する。再エンリッチメントと削除は引き続きサポートされる。

ソースの変更と、依存するチェックポイントの無効化は、ガード付きの1つの D1 バッチでコミットされる。バッチが失敗すると、元の記録とそのチェックポイントの両方が変更されないままになり、操作を再試行できる。忘却されたソースの掃除は、事実やトピックを削除する前に現在の忘却状態を確認するので、同じ custom ID の同時の復元は保たれる。初回バックフィルは、期限が来たプロジェクトをグローバルに探索し、その後、プロジェクト単位の集計で各対象の残りのソースを確認する。関連する移行は [storage-and-provenance.md](storage-and-provenance.md) を参照。

Workers AI は、前のチェックポイントと、次のソースバッチからの上限付きの抜粋を、信頼できないデータとして受け取る。その構造化された出力は、検証済み、未検証、未解決、次のアクションの主張を分けており、正確なメンバーシップは来歴を保つが、ソースのすべての詳細が要約で残ることを意味しない。生成されたチェックポイントは、統合された主張がプロジェクトの事実になることを避けるため、事実の抽出を行わない。

生成はトークン予算内の上限付き出力を要求する。切り詰めや無効な JSON は、同じ入力と簡潔なスキーマで1回だけ再試行する。再び無効なら公開せず、ソースを保留に残し、生成文を出さずに終了理由と出力長を記録する。リース取得後に既存のメンバーシップを確認し、古いチェックポイントを無効にしてから再構築するので、リビジョン不一致も通常の経路で回復できる。
