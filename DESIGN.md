# Design

Remnifold retains useful work history in a user-owned Cloudflare account so clients can recall it across projects without losing source provenance. The repository has two deployable parts: the server and the optional Codex plugin.

```text
Codex plugin                          User-owned Cloudflare account
  prompt/capture hooks  ───────────▶  Worker API
  MCP search/getDocument ◀─────────   D1 + Vectorize + Workers AI
Remote MCP client      ◀──────────▶  Worker /mcp + OAuth endpoints
```

`server/` owns authentication, persistence, lexical and semantic search, enrichment, and document retrieval. Each installation uses resources in the user's Cloudflare account. Codex client configuration selects that installation's endpoint and API key, plus recall settings. Remote MCP clients connect directly to the Worker without the local plugin; their client and model control recall and saving rather than Codex hooks.

## Local runtime and distribution

`native/` implements the local client in Rust. One executable provides `mcp`, `hook`, `capture`, `import`, `setup`, `status`, `plugin-bootstrap`, `plugin-update`, `server-setup`, `topics-setup`, and `memory-organize`; installed operation and server maintenance require neither Node.js nor Cargo. The stdio MCP server preserves the public tool schemas and structured/text responses, resolves a single client workspace root with a bounded request, and invalidates its shared context cache on root changes. The updater uses authenticated GitHub CLI and the official native Codex plugin CLI, preserving connection and registration rather than editing the plugin cache.

Platform packages are named `remnifold-<Rust target>.tar.gz` and contain a `remnifold/` root with `bin/remnifold` (`bin/remnifold.exe` on Windows), generated MCP and hook registrations, and `native-build.json`. The build manifest records the target, source commit, version, and SHA-256 digests of package files. Supported platforms are Windows x64, macOS Apple Silicon, and Linux x64 and ARM64; macOS Intel is outside the supported target set. `cargo xtask package` builds or accepts the exact target executable. Package creation and verification default to `--source-mode commit`: a real Git commit, clean source with no untracked source, and matching Git blob identities bind the source files to that commit. Explicit `--source-mode checkout` verifies local source bytes without establishing release-commit identity; the combined `cargo xtask check` uses this local verification for uncommitted development work. Installation uses the prepared platform package.

The Cloudflare Worker remains TypeScript in `server/src/`. The Rust workspace's `dev/` task runner downloads integrity-pinned native esbuild, TypeScript, and workerd tools plus Cloudflare types, then checks, bundles, tests, and packages without Node.js or a JavaScript package manager. The native executable embeds the Worker bundle and SQL migrations for server setup through Cloudflare REST. Production persistence remains D1; local server tests use real workerd with a test-only Durable Object SQLite adapter and deterministic AI/vector fixtures. Root and server `package.json` files retain version metadata for older consumer readers, without a package-manager dependency. Cargo dependencies are locked by the root `Cargo.lock`. Legacy connection aliases, state, capture identities, source provenance, and API contracts remain supported by the Rust implementation.

## Storage and provenance

Remnifold is the current product, plugin and repository name. Former Kagayoi Memory and Cloudflare Supermemory names are read-only connection, environment and state aliases. The renamed GitHub repository maps to its original canonical project identity and existing `kagayoi_memory` provenance label; persisted `sm_client` values remain compatibility metadata. Only the new plugin is enabled for normal operation. Existing server endpoints and Cloudflare resource identifiers are retained until a separately authorized deployment or migration.

The local client stores completed task records with deterministic v2 capture keys and custom IDs in the shared `memories` container. The server assigns a UUID on first insertion and retains it when the same custom ID is retried. Repository identity is stored separately as project provenance and does not partition new storage. The persisted `metadata.sm_project_id` field is retained as a 1.x compatibility contract alongside `metadata.project`; it is not a current product name. Existing records keep their server IDs and physical containers, and capture reuses a matching live legacy record instead of moving it. Forgotten legacy records are not reuse targets; retrying a forgotten shared record restores that canonical row. Manual saves also default to `memories`, with an explicit `containerTag` overriding storage. Manual forget accepts a document ID or exact stored content and is restricted to that explicit or default container; an ID must match a live record in the named container.

## Recall

Automatic context also includes up to two recent completed tasks from other sessions, regardless of topic or vocabulary. `maxRecentTasks` accepts integers from zero to three, with zero disabling this context. The hook requests `POST /v3/documents/list` with `projection: "index"`, `recentTasks: true`, and the current `excludeSessionId` when available. This mode excludes forgotten, opted-out, non-conversation, and consolidation records; it groups captures by project provenance and session before pagination. Each group uses its latest valid source timestamp, then turn, part, and revision ordering to select one representative. Source dates are normalized for comparison and fall back to the original storage creation date, so re-importing old work does not make it recent. The response declares `recentTasks: true`; clients ignore an ordinary list from older servers that do not support the mode. Normal lists and manual searches retain their existing behavior.

Recent summaries identify the source project, date, and document ID and are explicitly labeled as awareness cues without an assumed topic match. They reserve at most 1,000 UTF-16 code units inside the existing 3,000-unit hook context limit. Topic search and recent-task listing run concurrently under the same nine-second deadline, perform no additional embeddings for recent work, and retain successful output when the other request fails. Recent and topic entries use separate duplicate-suppression hashes, so seeing a short recent summary does not prevent a later relevant topic index from being shown. Records already injected as a topic index in the same response are not repeated in the recent section. Both channels recover after compaction or clearing.

Manual search also matches the stored project provenance name, including legacy project IDs with a readable repository name. For a project-name-only query, matching project records precede incidental mentions and newer source dates break ties before semantic similarity. Compound queries still prioritize topic coverage. Automatic recall keeps its content/topic matching rules and does not broaden eligibility from provenance alone.

Recall ranks concise metadata indexes by the user's current topic without restricting results to the current folder. The client requests `POST /v4/search` with `allContainers: true`, and the server searches all live containers with one query embedding and one namespace-unrestricted Vectorize lookup. Explicit `containerTag` and `sm_scope` searches retain their filters and revision checks. Lexical search remains available when AI or Vectorize fails; D1 semantic fallback remains bounded to 200 rows. An older server that explicitly rejects global search, or returns the legacy response shape, uses the former discovery and per-container path. That compatibility path is capped at 100 discovered spaces and reports a full page as incomplete; authentication, server, and network errors do not trigger fan-out retries.

Global responses declare `searchScope: "all-containers"`, list all live containers in `searchedContainers`, and set `spaceDiscoveryComplete: true`. This describes container coverage, not an exhaustive list of matching records: candidate scans and the final result count remain bounded. The client requires that response shape before accepting global results; malformed responses claiming global support fail instead of silently retrying every container. An empty client query performs no search request.

Automatic recall retains successful indexes when some spaces or legacy document fetches fail and reports the unavailable counts without exposing failed document IDs or exception text. The notice shares the existing hook context limit, and only injected indexes are recorded as read. A candidate that does not fit the remaining context budget is skipped while later, shorter candidates are still considered in relevance order; skipped candidates remain eligible on the next prompt.

Index descriptions and automatic queries omit Codex ambient browser-state envelopes, attached skill definitions, skill invocation links and Page-state envelopes, and project structured question replies into readable answers followed by their questions. Placing answers first preserves them when a long question reaches the description limit. Existing degraded descriptions are rebuilt from the available source request, or fall back to their saved title when only an index is available. Document reads omit attached transport envelopes from the user-request section while preserving assistant responses. This projection adds no document fetches and preserves explicit recall opt-outs. Existing stored source bodies, v2 capture identities, receipts, and persisted records are not rewritten. New captures omit these envelopes from their transmitted user-request content, but compute their v2 identity, part hashes and part boundaries from the original redacted source. Parts made empty by projection retain their IDs and part count and are excluded from automatic recall.

Automatic recall does not use general continuation or symptom reports alone as topic evidence; a standalone technical keyword such as `timeout` remains searchable. For continuation prompts it requires a complete `session_meta` row with an explicitly matching string ID within the first 64 KiB; the row need not be first. Missing, malformed or mismatched session identity prevents history recovery. It then scans backward in 128 KiB chunks up to 8 MiB and 16 preceding user messages; complete rows are limited to 256 KiB and larger or incomplete rows are skipped. A recovered topic is held while the scan checks preceding session metadata within those bounds, rejecting conflicting identity rather than trusting the candidate message alone. The scan shares the hook's nine-second search deadline and stops when 250 ms or less remain. Chunked reads recover topics before large tool outputs without retaining oversized rows or allowing unbounded history work. It uses this bounded scan to recover a concrete topic, excluding assistant output and injected context. Without a usable topic it performs no topic search; recent task retrieval remains independent. Automatic candidates for the same project, session, turn and part retain the newest available capture revision; manual searches retain historical revisions, and different turns, parts and consolidation checkpoints remain distinct.

Topic recall defaults to at most three memories; explicit settings up to five remain supported for automatic and manual search. The hook bounds total injected context to 3,000 UTF-16 code units, each entry to 1,800, and displayed topics to three per entry. With a session ID and readable transcript, the native recall state reader suppresses previously injected indexes by hashing the container/document identity, formatted index, and document/source update dates. State under `remnifold/recall-state/` in the selected Codex home stores hashes, the transcript path, and a byte offset, not conversation text. Session-start `compact`/`clear`, transcript compaction records, a changed transcript path or size below the saved offset, and incomplete transcript rows clear suppression. Transcript reads are bounded to the last 1 MiB of new data; exceeding that bound also clears suppression rather than risking a missed compaction. Missing session/transcript inputs or unreadable state/transcripts disable suppression, and failed state writes allow indexes to recur. This limits repeated context while preserving recall after context loss.

Automatic query extraction omits general action words and machine/account path prefixes while retaining dotted or hyphenated identifiers. Paths under development workspace names (`dev`, `projects`, `workspaces`, `repos`, `work`, including singular variants) contribute their project directory; other paths contribute their final component without inferring a file type. Index and legacy-heading matching normalize Unicode and identifier separators, reject unrelated ASCII word fragments, and allow an unversioned term such as `.NET` to match `.NET8`. Manual search retains its broader query extraction. Session start and prompts without topic terms avoid search and Git discovery.

Automatic recall requests `indexOnly` results. The server admits bounded direct index/topic candidates independently of Vectorize ranking, combines them with lexical and semantic candidates, and then applies the final relevance limit. It reads source content in chunks of at most 50 rows from at most 200 candidates, checking `updated_at` and `topic_revision` on reread to omit changed or forgotten rows. It derives compatible indexes for legacy documents without updating stored metadata and returns compact provenance and index metadata. SQL index matching uses Unicode case variants to retain non-ASCII uppercase labels. Missing query terms found in a source body can appear in a bounded 240-character original excerpt, labeled as an original passage rather than a new fact. Semantic scores alone still do not inject unrelated indexes automatically; manual search retains semantic-only candidates and full search excerpts, including matching original passages. Legacy servers still hydrate documents without indexes. `getDocument` provides complete source details when the current conversation and index do not contain the information needed for the task. Topic browsing uses its separate cross-container list API.

## Project consolidation

Project consolidation runs server-side rather than in lifecycle hooks. Records with a nonempty `metadata.sm_project_id` are grouped across containers by that provenance ID; records without one are grouped by physical container. Checkpoints are always stored in `memories`. The Worker keeps the existing 15-minute vector reconciliation schedule and uses a distinct daily cron at 18:00 UTC (03:00 JST) to inspect those groups. A new project becomes due when it has at least 20 unconsolidated records or three days have elapsed since its oldest pending record. After a successful checkpoint, the three-day interval is measured from that success. An initial backfill that has started but remains incomplete stays due so it can resume without meeting those thresholds again.

The first due scheduled run for a project drains its complete historical backlog through successive batches of at most 40 new records, carrying the prior checkpoint forward between batches. Recurring scheduled work handles one batch for each of at most 25 due projects per invocation. The authenticated `POST /v4/consolidate` endpoint and the MCP `consolidate_memory` tool use the same service. The endpoint applies normal due thresholds unless `force` is true; the MCP tool always sends `force: true`. Each manual request still processes at most one batch and requires at least one unconsolidated source record.

Migration `0005_memory_consolidations.sql` records consolidation state and exact source membership separately from user metadata. A published checkpoint is a new memory row; its persisted metadata contains a bounded source-ID preview. Global index-only recall returns `sourceMemoryIds` as the exact membership intersection with the final returned candidates, retains the total `sourceCount`, and sets `sourceMemoryIdsTruncated: true`, keeping ranking metadata bounded independently of project history. Explicit-container compatibility searches still return complete membership. Source rows are never deleted by consolidation. Publishing a replacement marks the former checkpoint superseded. Source upsert, update, re-enrichment, forget, or hard delete invalidates dependent checkpoints so stale or forgotten content cannot remain visible through them. Automatic recall first ranks matching query terms across indexes, topics, and original excerpts, then index/topic relevance without excerpts, and favors an active checkpoint when both are equal. Only a checkpoint in the final selection suppresses an original, and only when it covers that original's matching query terms; a specific detail omitted from a checkpoint can still expose its original. Manual search retains originals. Generation failures and failed publication guards do not publish a replacement or consume pending sources. A previous checkpoint remains active only while its own sources remain valid.

A request must acquire the project lease before starting generation. Publication checks the lease token, current revisions of the new sources, and the previous checkpoint's active state and source revisions, so a mutation during generation cannot publish stale content. Opted-out records are excluded from consolidation targets and new inputs; the prior checkpoint and its exact persisted sources must also remain recallable before generation and at publication. Migration `0011_consolidation_recall_opt_out.sql` invalidates historical active checkpoints containing opted-out sources, preserves the originals and membership, and resets initial backfill for clean regeneration; forgotten checkpoint vectors use the existing reconciliation cleanup.

Published checkpoints are generated records: direct document PATCH and custom-ID upsert return 409 before changing their content or metadata. This is checked against persisted consolidation membership rather than user metadata. Edit the original source records and regenerate the checkpoint instead; re-enrichment and deletion remain supported.

Source mutations and dependent checkpoint invalidation commit in one guarded D1 batch. A failed batch leaves both the original and its checkpoint unchanged so the operation can be retried. Forgotten-source cleanup checks the current forgotten state before deleting facts or topics, preserving a concurrent restoration of the same custom ID. Initial backfill discovers due projects globally, then checks each target's remaining sources with a project-scoped aggregate. Migration `0007_consolidation_project_index.sql` indexes the same provenance/container fallback expression without changing grouping or eligibility rules. Migration `0006_fts_indexed_updates.sql` limits UPDATE-triggered FTS work to changes in content or physical container; enrichment status updates retain the existing index.

Workers AI receives the previous checkpoint plus bounded excerpts from the next source batch as untrusted data. Its structured output separates verified, unverified, unresolved, and next-action claims; exact membership preserves provenance but does not imply that every source detail survives summarization. Generated checkpoints skip fact extraction to avoid turning synthesized claims into project facts.

Consolidation generation requests bounded output within the existing token budget. A truncated or invalid JSON response is retried once with the same source input and a more compact output schema. Two invalid responses publish nothing and leave sources pending; diagnostics record the finish reason and output length without logging the generated text. Consolidation also checks existing checkpoint membership after acquiring the project lease and invalidates stale checkpoints before rebuilding from live sources, so installations with old revision mismatches can recover through their normal scheduled or manual path.

## Codex organization

The plugin separates scheduling (`skills/setup-remnifold/`) from finite execution (`skills/organize-memory/`). Scheduling uses the official local Codex automation controls and the current Codex home/environment connection; it requires an explicit user choice and an available Codex app and PC. Each run resolves the installed executable afresh and processes one batch by default, at most two, with at most two lookup calls across the run. Auxiliary evidence reads remain targeted; unresolved work is deferred. Stored records and candidate summaries are untrusted evidence. This keeps model-generated conclusions in Codex's execution environment and avoids a second scheduler or an unbounded server generation loop. It trades unattended server execution for local app availability. The Worker cron still owns embedding/vector reconciliation and the separate Workers AI project-consolidation pipeline. User controls and CLI input are documented in [README.md](README.md#codex-memory-organization).

Owner-authenticated `POST /v4/organize/prepare`, `/commit`, `/lookup`, and `/sources` are exposed through the native `memory-organize` command. Existing MCP tool names and calls remain supported; getDocument adds optional source paging. OAuth credentials do not authorize the owner REST operations. The command uses the existing connection, accepts commit/lookup JSON through bounded stdin, and fails explicitly on unsupported servers rather than substituting save, forget, or Workers AI generation. Codex supplies the conclusions using its own execution environment; this server does not invoke a model to generate organization conclusions. Existing embedding and project-consolidation usage remains independent.

On Windows, `--line --private-stdin` requires a dedicated console and disables echo and line editing before emitting `REMNIFOLD_STDIN_READY` to stderr. This prevents source text from entering terminal output and avoids the cooked console line-length limit. The original console mode is restored after a complete CR/LF terminator, even if JSON validation fails. An unterminated timeout, oversized input or read failure leaves echo disabled until the dedicated PTY closes, protecting delayed payload bytes at the cost of requiring that PTY to be discarded. Redirected input and non-Windows hosts reject private mode before readiness; ordinary non-echoing pipes retain line/EOF compatibility. Input remains bounded to thirty seconds and 128,000 UTF-8 bytes. Model generation and safe input delivery stay client responsibilities.

Migration `0009_memory_organization.sql` keeps publication batches, exact source revision dependencies, original coverage, and private continuation progress outside user metadata. A prepare lease lasts thirty minutes and returns at most twenty records, 48,000 UTF-16 units of source text, and eight candidate summaries. Individual chunks contain at most 8,000 units and never split a surrogate pair. Four lanes rotate opportunities between multipart groups, partial continuations, due-deferred records and untouched records; empty lanes yield to the next lane. Continuation lanes inspect fixed raw ID windows before eligibility checks, and fresh discovery inspects at most 512 raw IDs per window. Stable keyset cursors prevent a growing untouched queue from starving continuations; this does not promise that every lane appears in each batch. The shared text budget still applies. Metadata is projected to bounded necessary fields; meaningful long identities are not truncated. JSON UTF-8 bytes, including escaping, must fit below 1 MiB before a lease is inserted, reducing candidates/sources when necessary. Existing classifications are hints, not separate mandatory jobs. Lookup accepts one bounded search phrase to find more existing summaries; semantic uniqueness is not guaranteed.

Automatic deferrals retry after one hour on the database clock. Within each bounded 64-ID continuation window, due records and groups are ordered by retry time and then ID; partial commits rejoin at the database clock. Matching non-active multipart groups supply the retry priority in progress and fresh discovery, so stale per-document timestamps cannot repeatedly win after group continuation. Revision-matched progress also respects the group retry deadline. Invalid groups receive untouched priority for coverage recovery and use the source retry deadline, matching the existing invalid-group reset without rewriting stored deadlines. Untouched fresh records use their stable database created_at as enqueue age; ordinary updates do not reset creation, and this is not a historical decision date. Multipart selection retains priority among equal retry times; a later multipart candidate cannot displace the preceding ordinary prefix. Fairness is bounded to each raw window, not global chronology. Migration `0012_organization_retry_fairness.sql` moves future legacy zero-offset deferrals and deferred-group deadlines 23 hours earlier, preserving the original deferral time plus one hour and leaving past deadlines, partial progress and all other state unchanged. Capture conflicts still suppress automatic retries until resolved; cooldown expiry alone does not reconcile them.

Summary partitions use the physical container, actual string sm_scope (or absence), sm_project_id (or absence), project display name (or absence), and recall class. Server-computed fingerprints are persisted while exact values are re-read under revision guards for publication. Updates cannot cross partitions. A bounded filepath is inherited only when all represented dependencies prove the same nonempty value; mixed, unknown or oversized paths remain available through original-source retrieval. Explicit stored recall exclusion stays excluded, legacy derived manual-only records carry an internal manual-only marker, and automatic records remain eligible; classes cannot be mixed. These organization markers are authoritative only for registered generated versions: ordinary documents may contain identical user metadata without changing capture, discovery or recall behavior. Default index-only searches exclude registered manual-only summaries; explicit remote MCP manual searches admit them while retaining stored-false exclusion. Manual native search remains available. Summary indexes preserve meaningful headings and bullets without changing capture heuristics; punctuation-only output cannot be published.

Both native and server index reconstruction honor stored `recallable: true` on supported version-1 indexes with `sourceKind: "organization"`, even for short authored conclusions that conversation-capture heuristics would omit. Explicit false remains authoritative. This preserves authored summary eligibility without broadening the low-information capture heuristic.

Commit accepts up to eight summaries (24,000 output units total) and one coverage assertion per prepared source. References within that commit connect each source to every conclusion required to represent it. Complete coverage requires the final chunk and a verified complete capture-part set; partial coverage saves only a bounded private continuation memo and offset, and deferred coverage postpones that revision for one hour. Incomplete and uncertain records stay visible. Semantic completeness is an assertion made by Codex, not something the schema or server proves. All important topics, unresolved points, conclusions and their reasons must survive before Codex declares complete. A changed revision discards its private progress and starts again.

Multipart capture identities use group/member/group-summary state. Discovery and reading commit only private groupProgress memos and cursors, without public summaries or coverage. All parts of one capture version and every chunk must be read before a final anchor becomes ready; finalization guards all members and publishes the summary/whole-group logical coverage atomically. Missing, changed, forgotten or conflicting-partition members invalidate or defer the group. Source creation/update, source-metadata dates and summary generation are distinguished: conclusions retain evidence IDs and their known decision times or uncertainty. Turn ordering applies only when independently reliable within a session; verified capture variant counters do not establish a newest version; cross-session or unknown chronology never justifies mechanically superseding a decision merely because an older record was imported later.

The logical capture identity follows the existing effective project/container, session, turn and part semantics. Multiple document IDs for that identity defer as duplicates even if their contents match, except distinct-key single-part v2 captures with exact key shape and server-verified SHA-256 of the unchanged body after the exact current or historical wrapper. The captureVariant marker identifies independent evidence, never a latest version or trustworthy turn chronology. Hash-unverifiable bodies cannot use the conflict exception and defer with capture-hash-unverifiable while the coarse capture conflict remains. A lone projected capture retains ordinary eligibility with no verification marker or proof, and uses the strict conflict guard on commit. Migration 0010 retains the old strict conflict view for rollout safety; the new Worker uses the shape-aware blocking view and proves body hashes again on commit. Coverage records bind that proof to the exact source revision; absent or stale legacy proof remains subject to conservative invalidation on a new capture peer. Targeted HTTP prepare accepts up to twenty unique sourceIds and bypasses only automatic retry suppression/cooldown while preserving revision-matched offsets and memos, eligibility, leases, partitions and response bounds; no original is hidden or merged across revisions. Once deferred, the same source revision, dependent checkpoint, or deferred multipart group is not selected again while its capture conflict remains; resolving the conflict restores eligibility after the existing cooldown, and source edits discard private progress. The official retry that reuses one canonical document ID remains unchanged. Integer turn/part values outside the safe numeric range preserve the original and defer organization, while ordinary fractional metadata does not by itself make a document ineligible. These checks do not introduce a new revision-merging state or claim that an LLM has reconciled every historical revision.

Publication verifies the lease, previous summary versions and every exact source dependency inside one D1 batch. Identical committed requests return the stored response; different content for that batch returns conflict. Pending snapshots contain IDs, revisions and cursors rather than copies of source bodies, metadata or continuation memos. Completed receipts retain a request digest and response IDs and discard the snapshot. Summary rows are immutable through normal document save/update APIs. Coverage hides originals from ordinary search and automatic topic recall only while all its required summaries remain active. Recent-task awareness keeps its existing conversation eligibility, session grouping, chronology and pagination. Ordinary lists and getDocument still expose live originals. Forget and opt-outs retain their existing meanings; organization never restores or deletes an original.

SQLite triggers invalidate coverage and derived summary memories on effective source edits, reclassification/re-enrichment, forget, restore and hard deletion, including direct SQL mutations. They ignore vector bookkeeping, operate before source deletion and do not require recursive triggers. Derived facts/topics are removed and vector deletion is left pending for reconciliation. Failure rolls back the mutation and invalidation together. A source represented by several summaries reappears when any required summary fails.

With AI enabled, organization summaries use embedding-only background enrichment and bounded retries on the existing reconciliation cron; they never request fact generation. This consumes existing Workers AI embedding usage. A summary-specific database-clock CAS claim coalesces concurrent work. Attempt tokens fence D1 writes and Vectorize mutations, and late writes repair the current D1 embedding/token rather than publishing an obsolete attempt. Expiry recovery can still overlap an external AI call that has not returned. General enrichment retains its existing contract.

Coverage completion is separate from mode-dependent search visibility. Prepare does not select completed coverage again while embeddings are pending. With AI enabled, sources with stored embeddings remain visible until every required summary has a current embedding and an indexed vector; failures leave them visible. With AI disabled, complete lexical coverage hides them without waiting for embeddings. Enabling AI admits those originals again until retries of disabled/pending/failed summaries establish readiness. Explicitly opted-out legacy sources retaining embeddings defer instead of triggering enrichment. Reconciliation preserves original vectors while AI is disabled and their semantic replacements are not ready. It deletes semantically covered hidden vectors as well as forgotten vectors, rechecks D1 after asynchronous mutations and restores reappearing originals from their existing embeddings. While hidden vectors still occupy topK, a bounded 200-row D1 semantic fallback also admits indexed candidates; it does not guarantee exhaustive recall. If previously deleted original vectors become eligible again, FTS and direct retrieval return immediately, while bounded reconciliation restores stored embeddings without re-embedding. Queue length, retry failures and external vector visibility mean the fifteen-minute cron interval is not a completion deadline.

The read-only sources endpoint and native CLI return recorded source IDs/container/dates in stable keyset pages of at most fifty, excluding forgotten rows. Direct dependencies and multipart members are paged hierarchically. A checkpoint source is an intermediate record whose getDocument preview/cursor leads to its exact recorded membership; missing historical membership is not invented, and separate provenance paths may repeat a source. Cursors bind the parent revision. getDocument adds a five-row organizationSources preview for generated versions recorded in memory_organization_versions and checkpoints recorded in memory_consolidations; cursor requests bypass document-body reads and return source pages only. A replaced or invalid generated version returns conflict, including replacement during retrieval. User-supplied metadata cannot impersonate the generated-version registry. Remote MCP forwards this additive preview and paging; installed older native clients use the separate sources CLI when they discard unknown fields.

Legacy project checkpoints are eligible as whole records. Associations join the existing exact checkpoint membership as additional invalidating provenance without expanding it into snapshots or copying all its rows. Existing organization summaries retain their prior membership on replacement and insert only the current bounded additions. Missing checkpoint membership is not invented. A checkpoint is hidden only after its own complete coverage, so old information can remain visible through an unprocessed checkpoint. The existing project pipeline continues reading live originals, including organization-hidden ones, but excludes generated organization summaries to avoid a generation loop. Checkpoint replacement conservatively invalidates dependent organization summaries and permits reprocessing. SQL verification still reads work proportional to exact historical membership and remains subject to D1 limits; a failing checkpoint can be marked deferred in an uncommitted batch while the other sources proceed. Neither this protocol nor a finite run claims that the whole archive has finished.

## Capture

Capture retains JSON sent-document receipts and coordinates their updates through SQLite under `remnifold/capture-state/` in the selected Codex home. It unions receipts from both former `kagayoi-memory/capture-state/` and `cloudflare-memory/capture-state/` locations and writes future updates to the current location, preventing an upgrade from resending acknowledged turns. Deterministic capture keys and retrying unacknowledged records preserve retry safety; the configured memory API key and supported secret patterns are redacted before capture. Current records keep session and part bookkeeping in metadata instead of the user-facing body. Retrieval removes only the exact generated header from legacy v2 bodies, preserving unmatched user Markdown and existing split boundaries. Codex's official local memory store remains outside this integration.

Capture redacts every nonempty configured key and the complete value of supported quoted secret assignments, including spaces and escaped quotes. History discovery limits concurrent metadata readers while retaining full candidate comparison, ordering, and the final import limit. UTF-16 length limits avoid cutting a surrogate pair in displayed titles, indexes, queries, and new document bodies. V2 identities continue to use the original title-length and fixed-part hash calculations; safe output boundaries do not change existing custom IDs, capture keys, or acknowledged receipts. Existing stored records and receipts are not rewritten by this client change. Capture failure output contains only fixed stage, cause, and action codes; exception text, local paths, settings, and HTTP responses are excluded. `repair-required` identifies failures such as invalid receipts that repeated retries alone cannot repair.

## Enrichment and topics

Migration `0004_content_topics.sql` adds revisioned `memory_topics` rows and classification state. Workers AI extracts content topics alongside facts; explicit validated `metadata.topics` can supply labels. Topic labels describe content, while containers remain physical storage and project metadata remains provenance. Fact support and supersession lookup is restricted to matching project provenance within a container, so shared storage does not make one project's facts replace another's.

`POST /v4/profile` applies the requested `sm_scope` to source memories in both its empty-query fact aggregate and its document fallback; a nonempty query uses scoped search. Omitting scope retains the legacy container-wide profile. Scope therefore constrains derived facts as well as source retrieval.

`GET /v4/topics` lists topic counts and an unclassified count. `POST /v3/documents/list` spans all containers by default, with optional container and normalized exact-topic filters; `__unclassified__` selects records without current topic rows. Its optional `projection` selects the compatible full response or the compact `index`, `ids`, and `capture` shapes used by bundled callers. The topic setup batch also sets `enrichmentEligible` so opt-out records do not block older classification targets. Topic reads join against the document's current revision and omit forgotten records. Updates and enrichment retries replace the revision; guarded D1 batches prevent stale work from publishing topics or facts. Re-enrichment changes the revision and invalidates dependent checkpoints atomically. Re-enriching a checkpoint preserves its disabled fact extraction, removes any facts previously derived from a legacy checkpoint, and restores supported source facts in the same guarded transaction. Updating or forgetting a record removes its derived fact/topic rows and reactivates facts that no remaining live record supersedes.

Enrichment is asynchronous and independently tracks embedding, vector, fact, and topic outcomes. Records with `metadata.memoryIndex.recallable` set to `false` remain stored and manually searchable, but are excluded from automatic recall and automatic embedding, fact, topic, and vector enrichment; explicit topics are still stored. Disabled, failed, or deliberately skipped classification leaves records available through unclassified browsing. The native `topics-setup` command previews a bounded enrichment-eligible batch from that view; `--apply` submits those IDs to `POST /v4/enrich` using the existing backend, without adding a queue service. Acceptance is not completion, and re-enrichment refreshes other derived data too. This keeps classification within existing Workers AI usage at the cost of requiring callers to observe completion before selecting another batch. Server migrations precede clients that depend on topic APIs.

Unexpected enrichment failures log the document revision and mark only pending or processing stages failed when D1 is available, preserving completed stages. These updates retain the same revision and forgotten-record guards as enrichment publication. A second failure while recording the status is logged separately, and the original background rejection remains visible to Workers. Partial enrichment failures also log `memory_enriched` with `ok: false` and stage errors; outer scheduled failures log `scheduled_failed` with the cron and rethrow. Error diagnostics redact the configured `MEMORY_API_KEY` and limit the error message to 2,000 characters.

## Vector reconciliation

Vectorize entries carry the document revision, while D1 remains authoritative for search and reconciliation. Vector status and reconciliation split lookups into batches of at most 20 IDs. Forgetting a record or superseding a checkpoint marks its vector for deletion; the 15-minute reconciliation rechecks forgotten rows and retries removal even when AI enrichment is disabled. A late upsert that loses its D1 revision guard is cleaned up, and a concurrent delete of a restored active record re-registers its current vector. Failed or still-visible deletions remain eligible for later reconciliation.

## Provisioning

The native `server-setup` command handles Cloudflare REST discovery, resumable provisioning, migrations, deployment, and endpoint verification. Its default is authenticated read-only discovery; `--apply` enables changes. Authentication uses `CLOUDFLARE_API_TOKEN` or `--token-stdin`, without importing Wrangler OAuth credentials. Explicit names take priority over an existing JSONC configuration supplied with `--config`; that input is never overwritten. Without explicit names, discovery reuses `remnifold`, then `kagayoi-memory`, then `cloudflare-supermemory`. Configured resource identities must match the selected account and discovered resources. Existing bindings, schedules, and routes are preserved, with incompatible configuration rejected rather than silently replaced. Custom domain and route changes require the corresponding extra Cloudflare permissions.

Resume state is stored outside the repository and plugin at `<CODEX_HOME>/remnifold/server/config.json` (default `~/.codex/remnifold/server/config.json`), or the absolute external path supplied by `--state`. Paths with linked ancestors and using the configuration input as state output are rejected. Generated resource identifiers and credentials are not source assets.

Migrations run before deployment and client changes; the additive OAuth migration retains existing documents, physical spaces, provenance, and `sm_*` metadata. A supplied memory key enables authenticated session, remote MCP initialization, and required tool discovery checks. Without the local key, setup retains the existing secret and reports that authenticated verification was skipped. Failed steps can be resumed against the same resources. Capture receipts remain in the existing Codex home and are not migrated to the server.

## Remote MCP

The stateless Streamable HTTP endpoint is `/mcp`. It accepts the existing API key as a Bearer credential or MCP-scoped OAuth access tokens issued through protected-resource and authorization-server discovery, public dynamic client registration, authorization code with PKCE S256, refresh, and revocation. Owner consent requires the existing API key. OAuth tokens do not authorize the existing REST API. Remote tools search existing spaces and retrieve or save records using the same backend; they do not move or duplicate stored memories. Server instructions ask clients to search, open details when needed, and save durable results, but client and model behavior determines whether tools are called. The Codex stdio transport and hooks remain separate and unchanged.

`server/src/mcp-oauth.ts` owns discovery and OAuth credentials persisted by migration `0008_remote_mcp_oauth.sql`. The Worker router checks credentials and browser origins before calling the transport adapter in `server/src/mcp.ts`. The adapter validates tool arguments and invokes the existing REST routes internally with the owner API key, retaining their storage and mutation rules. OAuth consent therefore grants access to the installation's memories, not an isolated per-client collection. Remote saves accept explicit `projectId` provenance; they do not infer local workspace folders. Remote consolidation also requires an explicit `projectId`, unlike the Codex stdio tool's workspace-root fallback.

Remote saves use the same secret redaction implementation as Codex capture, additionally removing the current OAuth credential. A supplied idempotency key is scoped to the physical space, project, and redacted content so retries reuse a record without overwriting a different project's memory. OAuth access tokens expire after one hour; refresh tokens rotate and expire after 30 days. Reusing a refresh token revokes its token family, and changing the owner API key invalidates issued credentials. Registration is limited to ten requests per source IP and origin per hour. Unapproved registrations expire after 24 hours; approved client identities remain valid. Browser MCP requests require the server's own origin or an exact comma-separated origin in `MCP_ALLOWED_ORIGINS`; server-to-server clients normally send no Origin header. OAuth consent always requires the same origin.

Authorization forms use `Referrer-Policy: same-origin` to preserve the consent POST's Origin. Their CSP keeps `form-action 'self'`. After Allow or Deny, the server returns an HTTP 200 completion document with a script-free meta refresh and a fallback link to the fully validated callback URL. This ends the form-submission navigation before the application's own redirect chain, so Chromium does not apply the form's CSP to downstream application hosts. Completion responses use `no-store` and `no-referrer`, clear the consent cookie, and do not forward the form body or owner key. Callback URLs are HTML-escaped without changing their registered identity, state, or code; exact redirect matching during authorization and token exchange remains required, and null and foreign consent origins remain rejected.

## Plugin integration

Codex loads an installed plugin copy from its cache. Remnifold uses the `remnifold` plugin ID and platform distribution directories under `dist/<target>/remnifold`. Connection files in the selected Codex home (default `~/.codex`) are read in the order `remnifold.json`, `kagayoi-memory.json`, then `supermemory.json`; setup writes the current file while retaining the former files. Environment overrides and user upgrade steps are documented in [README.md](README.md#upgrading-from-1x-names). Capture receipts and recall state live outside the plugin cache, so reinstalling the plugin does not discard them. Recall reads the current state first, then falls back to `kagayoi-memory/recall-state/` or `cloudflare-memory/recall-state/`, and writes only to the current location. Hook trust is managed by Codex and requires review of each current definition. A new task picks up updated skills and MCP tools.

The package uses Codex's `.codex-plugin/plugin.json` format because Codex 0.153.4 does not load lifecycle hooks from portable Agent Plugin manifests. Its generated native MCP configuration sets `cwd` to `.`; Codex resolves that directory against the installed plugin root. The launcher path is relative to that root, while workspace provenance comes from MCP roots or an explicit `sourceFolder`, never the server process directory.

The Rust packager in `dev/` constructs an allowlisted platform archive with generated native MCP and hook registrations. Output paths are checked for linked ancestors and repository outputs must remain under `dist/`. Verification checks the archive against the same source checkout and exact executable before publication.

Windows packages add `commandWindows` overrides for all four hooks, using a fixed Git for Windows shell to launch the native executable. The packager and updater share the launcher definition in `native/src/hook_command.rs`. The outer command contains only a fixed octal-encoded script; Git Bash reads and quotes `PLUGIN_ROOT` from its environment, keeping plugin paths out of outer-shell expansion and preserving the original stdin. This supports Unicode and shell metacharacters in plugin paths while avoiding workspace or `PATH` shell resolution. The normal direct commands remain for macOS/Linux and historical packages. Updater validation accepts either no overrides or the complete exact Windows set, rejecting partial sets and overrides on other targets. For an incoming package using these overrides, Windows `--apply` checks shell location and executable resolution before changing the installation. This is an installation-time prerequisite check, not continuing validation of Git or proof that an already running Codex inherited a usable environment; user requirements and recovery steps are in [README.md](README.md#requirements).

### Release installation

CI verifies the final plugin archive against the clean packaging checkout and its actual Git commit before publication. A source-commit string in `native-build.json` alone is insufficient; commit mode verifies source identities against that Git tree. Checkout-mode test archives do not establish publication readiness. Native archives must match the allowlisted source files, generated platform registrations, and the exact executable built for that target; `native-build.json` binds their digests to the source commit and target. Cargo, plugin, server, and build-manifest versions must match the root package version. Older published JavaScript archives are migration inputs for isolated updater tests rather than newly built packages. This checks the uploaded archive itself in addition to validating the staged plugin directory. The command and required ordering are maintained in [AGENTS.md](AGENTS.md#validation).

The packaged `plugin-update` command updates `remnifold@personal` on Windows, macOS, and Linux when explicitly requested. The default repository is `1llum1n4t1s/remnifold` and the non-Git marketplace source is `~/plugins/remnifold`; `--config` can supply `localPlugin` settings. It uses authenticated native GitHub CLI and Codex CLI, preserves connection/capture state, and does not deploy the server.

Distribution configuration in the release Git tree selects R2: private `remnifold-builds` stages archives and public `remnifold-updates` serves `https://remnifold-updates.kagayoi.com`. Current releases contain Windows x64, macOS Apple Silicon, and Linux x64/ARM64; macOS Intel is excluded from new builds and distribution. Windows keeps its native CI build. macOS is built on the Apple Silicon SSH host `mac`, and Linux is built on GitHub-hosted runners (`ubuntu-latest` for x64, `ubuntu-24.04-arm` for ARM64). Those three Unix packages are checked against the frozen clean source commit and placed into immutable private `local-inputs/<commit>/<target>/` objects before branch push. CI verifies the complete input archive, source, target, version and digests, then stages it under the actual CI run/attempt identity. These are owner-trusted local builds: the GitHub witness proves CI verification and publication acceptance, not independent execution of the local build or tests.

All four native-package jobs must succeed before the publisher verifies the staged objects and source, writes immutable public archives and a release manifest, creates a traceability status, and switches the version index with conditional writes. Local input records are strict and create-only: repeated identical inputs require matching full bytes, conflicting records fail, and a missing input fails without waiting for an external build. An accepted index is immutable across retries; a successful retry proves the prior publication using its publisher logs and full object bytes instead of relabeling it. A provisional failed/cancelled/timed-out publication can be repaired only after verifying its candidate logs and complete previous object root, with an ETag compare-and-swap protecting the index. R2 transport, build, test, packaging, and publication use no executable JavaScript Actions or Node.js.

CI runs on pull requests, manual dispatch, and branch pushes except `dependabot/**`; tag pushes do not run CI. Windows executes the native/server/client/package/updater checks. Unix jobs import and stage local inputs only for trusted `release/*` pushes; main, pull requests and manual validation skip those distribution operations without receiving distribution secrets. Their successful source checks therefore do not claim Unix build or runtime coverage. Unix runtime checks run on `mac` and the GitHub-hosted Linux runners before the release inputs are uploaded. Publication is verified on `release/*` branch pushes rather than tag pushes and requires all four staged targets.

All four `native-package` jobs run on GitHub-hosted `windows-latest`. `publish-r2` runs on GitHub-hosted `ubuntu-latest`. Publication separates Cargo output, validation state and temporary files under a run/attempt-specific directory in `RUNNER_TEMP`. The publisher receives release credentials only through `r2-release`; the publication job is gated to the repository's exact release-push workflow and successful package matrix.

GitHub Environments control credentials. `r2-staging` allows pushes from `main` and `release/*`; `r2-release` allows `release/*`; `validation` has no distribution secrets. Deployment policies use selected branches (`protected_branches: false`, `custom_branch_policies: true`), not `ref_protected`. These policies reject PR distribution access but do not themselves protect global branches. The existing trust model includes the repository owner and people with repository write access; the repository currently has one owner. Staging keys are limited to private staging objects; release keys have only the necessary object permissions in the staging and public buckets. Only the publisher receives commit-status write permission.

A commit status can point to an arbitrary URL and is traceability, not proof that GitHub produced a release. The updater resolves `release/<version>` to its actual commit and plugin version, verifies the exact CI workflow path/ID, both repository IDs, push event, release branch, commit, and latest successful run/attempt. It requires a unique successful `publish-r2` job in that attempt and fetches its GitHub-generated raw logs with a 4 MiB bound. After stripping valid GitHub timestamp prefixes, a schema-2 release requires exactly one `REMNIFOLD_R2_MANIFEST_V2` record and four unique `REMNIFOLD_R2_ASSET_V2` records. Historical schema-1 releases instead require V1 records and all five historical targets. Index, manifest and witness schemas must agree; mixed, missing, partial, duplicate, unknown-target or mismatched records fail closed. The witness binds the manifest hash and archive key/hash/size, independently of R2 and the status URL. Receipt schema 2 remains a separate format from the release schema.

Old updaters cannot authenticate the new four-target format and fail closed. The transition uses the signed Windows bootstrap or trusted-source Unix bootstrap to obtain a new updater once, preserving connection and registration. New readers keep historical five-target metadata and receipts valid. Existing release branches and immutable objects are retained because shipped clients and receipts still resolve them; historical Intel metadata is not a current build target.

The updater downloads R2 objects only from the configured origin without redirects, verifies the manifest/archive and native-build digests, and checks allowlisted files, target/version identity, and source bytes against the release Git tree before installation. Schema-2 receipts record publication run/attempt separately from witness run/attempt/job, plus verified package identities. Retain `verified-<commit>-<target>.json`: later `--verify-only` checks installed source/cache against the receipt and release source without requiring retained R2 objects or CI logs; GitHub release ref and source metadata remain required. GitHub job-log retention is a fresh-install boundary; expired witness logs prevent a new fetch even if R2 still serves the archive.

Old release commits without distribution configuration retain GitHub Actions artifacts and schema-1 receipt compatibility, including published 1.0.15 JavaScript/native packages. A present but invalid R2 configuration or invalid publication cannot fall back to the legacy transport. Legacy artifact ZIP validation retains exactly one expected tarball entry, consistent ZIP headers, bounded expansion, and safe allowlisted tar paths.

An old executable cannot implement the new R2 discovery path. Windows uses Rust `plugin-bootstrap`, obtained from a trusted source build or a separately authenticated immutable GitHub Release asset. The asset is the exact executable from the CI-verified Windows R2 archive, bound to the release commit. GitHub release and asset signature verification with native GitHub CLI 2.93.0 or newer establishes the first executable's trust before execution; an unverified R2 helper cannot authenticate itself. The file remains in a trusted private directory between download, verification, and execution. This separates the initial executable trust root from the R2 publisher-log witness that the executable subsequently verifies. The publisher checks the draft, exact asset, tag and immutable-release settings before sending publication once. An accepted PATCH ends publication without release/tag re-fetch or signature verification; the local receipt records acceptance rather than public availability. A receipt-write failure after acceptance is reported separately so it does not invite an automatic resend. User acquisition still verifies signatures before execution. The publication procedure is maintained in [AGENTS.md](AGENTS.md#bootstrap-release-publication), and user acquisition steps are in [README.md](README.md#connect-an-existing-server).

The native bootstrap shares the updater's publication and package validation. Default mode checks publication without installing, invoking Codex, or requiring an installed plugin; download-only returns the unchanged verified formal archive without executing its contents. Explicit apply delegates installation to the updater and then verifies its receipt. Publication checking and download-only create no installation receipt; apply can retain a receipt even if a later installation step fails. Unix retains the trusted-source `scripts/bootstrap-plugin.sh`, using native GitHub CLI, curl, and OS shell/hash/tar tools to authenticate the same publisher witness before delegating to the verified executable. Its default mode verifies that the authenticated release tree contains native bootstrap support and invokes `plugin-bootstrap`; unsupported older releases require download-only or a trusted current native bootstrap targeting that version. This avoids consulting plugin installation state merely to check publication. Neither route sends GitHub credentials to R2. GitHub CLI's raw-log escape flag is detected from help for compatibility.

Bootstrap invocation state stays outside the repository, plugin source, and Codex home. Windows resolves existing physical prefixes, including short-name aliases, and rejects linked or overlapping paths. Download-only delivers a rehashed copy under a new private OS-profile `Remnifold/Downloads/<UUID>` directory, separate from D: processing state. Persistent ancestor ownership and ACL checks and held directory handles protect delivery against replacement; unsafe existing ACLs are rejected without changing them. Unix requires root/current-user-owned ancestors and rejects writable non-sticky parents; macOS accepts only strictly parsed deny-only ACLs. These checks preserve existing safe permissions instead of repairing arbitrary directories.

The shared native subprocess runner bounds stdout and stderr while reading. Windows children start suspended, join a kill-on-close Job Object, and only then resume; limits and timeouts stop the full job tree. Unix uses an isolated process group, matching the Bash bootstrap; intentionally daemonizing descendants that leave the group are outside that containment boundary. Raw logs and secrets are not printed. Invocation-specific state is retained until safe cleanup under the rules in [AGENTS.md](AGENTS.md#standalone-local-plugin-update).

The updater rejects linked paths, unexpected files, obsolete managed files, and source edits that match neither the installed cache nor the incoming release. It copies validated files into the configured marketplace source and invokes the official `codex plugin add remnifold@personal` command; it does not write the plugin cache directly. Source copying and CLI installation are not one transaction: a CLI failure can leave the source updated with the prior cache still installed. A retry accepts that state and finishes installation; an exact match of version and both file sets returns `already-current`. Connection and receipt state remain outside these managed files. Installation verification does not establish that an existing chat reloaded the plugin or trusted its hooks. Updater execution, isolated E2E validation, and temporary-file cleanup are maintained in [AGENTS.md](AGENTS.md#standalone-local-plugin-update).

Repository entry points are `.codex-plugin/`, `.mcp.json`, and `hooks/` for source plugin wiring; `native/` for the client, maintenance commands, and updater; `dev/` for the Node-free toolchain, packaging, and contract tests; `server/` for the Worker and migrations; and `skills/setup-remnifold/` for the setup workflow. Source registrations use Cargo while installed registrations use the packaged executable. Development checks are maintained in [AGENTS.md](AGENTS.md); installation and operation are in [README.md](README.md).
