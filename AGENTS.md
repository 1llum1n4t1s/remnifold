# Repository guidance

This repository packages the Remnifold self-hosted Cloudflare server and its standalone local app for Claude Code and Codex.

- Keep all local client and maintenance commands in `native/`, and development, build, packaging, and tests in the Rust workspace's `dev/` task runner. Windows, macOS, and Linux paths must run without Node.js, npm, pnpm, or Wrangler. Preserve existing public tool, HTTP, state, and capture-identity contracts.
- Keep the Worker TypeScript source in `server/`, bundled by native esbuild and deployed by the native `server-setup` command through Cloudflare REST. Production persistence stays in D1; the Durable Object SQLite adapter is test-only. Avoid new dependencies.
- Keep Remnifold's own configuration and state in the app folders resolved by `native/src/paths.rs` (`REMNIFOLD_HOME` override, then OS-standard locations), never in a Codex or Claude Code home. Read the former Codex-home connection and state only for migration, never delete it, and isolate every test process with `REMNIFOLD_HOME`.
- Preserve the storage, provenance, recall, enrichment, and organization contracts in [DESIGN.md](DESIGN.md), including 1.x connection/environment readers, legacy capture receipts and spaces, existing document IDs, owner identities, and persisted `sm_*` metadata.
- Keep the official Codex local memory store outside this integration. Capture must retain deterministic keys/custom IDs, retry-safe document reuse, and redaction of the configured memory API key and supported secret patterns.
- Never commit API keys, generated resource IDs, `.dev.vars`, `.wrangler/`, or generated provisioning state. Metadata-only root/server `package.json` files support older version readers; they do not authorize restoring a JavaScript package-manager toolchain.
- Current build/distribution targets are Windows x64, macOS Apple Silicon and Linux x64/ARM64. Build every target in `ci.yml` on its native GitHub-hosted runner (`windows-latest`, `macos-latest`, `ubuntu-24.04`, `ubuntu-24.04-arm`); exclude macOS Intel from current builds and checks, though historical schema-1 Intel metadata stays readable.
- Run the affected [Validation](#validation) checks and `git diff --check`.
- Localization: human-readable text (CLI output and help, the Setup welcome, hook notices, recall headings) is looked up through `locale::tr`/`tr_with` from the nine dictionaries in `native/src/locales/` (see [DESIGN.md](DESIGN.md#localization)). When you add or change human-readable wording, update all nine dictionaries and keep the consistency tests passing. AI-facing text (MCP tool descriptions and schemas, instructions returned to the model) stays English. When you change `README.md`, change every `README.<tag>.md` in the same change.
- Do not deploy, migrate a remote database, publish, stage or live-smoke R2, create a remote repository, push, run `topics-setup --apply`, run `server-live-test`, invoke remote consolidation, or run `memory-organize prepare`/`commit` without an explicit request. Organization prepare creates a lease and is not a read-only probe. Pushing a version tag `v<x.y.z>` starts the R2-writing `release-velopack.yml`, and a `release/*` push starts the R2-writing strict publication in `ci.yml` (frozen at 1.0.32; create no new `release/*` branch), so either needs the same request. Local verification does not authorize remote changes. The same applies to the real installation: never run a Setup installer, `install`, `connect` or `setup` against the user's real app folder, configuration, `settings.json`, Claude Code/Codex registrations or HKCU `Run` key while validating; use the isolation described in [Setup installer (Velopack)](#setup-installer-velopack).

## Standalone app installation

There are two installation routes. **Setup (Velopack) is the default for ordinary users** (see [Setup installer (Velopack)](#setup-installer-velopack)); its owner-decided trust model (HTTPS from R2, Velopack feed hashes and platform code signing, no `gh` requirement) is in [DESIGN.md](DESIGN.md#setup-installer-velopack). The **strict `install` route below stays for advanced users and must not be removed or weakened**: it keeps requiring authenticated GitHub CLI and the CI publisher-log witness, the `versions/`/`receipts/` and fixed-executable replacement contracts, and coexistence with a Setup installation (separate app folders). **The strict route is frozen at its final version 1.0.32** (owner decision, 2026-11-18): new versions are published only as Setup (`win`, `osx`, `linux-x64`, `linux-arm64`, from a version tag), and no new strict publication (`release/*` branch, `releases/<version>/index.json`) is made. Keep the strict code (`install`, `--verify-only`), `ci.yml` (its path and `publish-r2`, which old clients' witness verification depends on), the existing `release/*` branches and the `releases/` objects unchanged; do not re-run old publication runs.

When explicitly requested, install or update the app with `install --version <version>` per [README.md](README.md#install-the-local-app): publication check, `--apply`, then `--verify-only` with the same version (authenticated native GitHub CLI, no Codex). Keep `--work-root` outside the app, configuration and repository folders without linked ancestors. Do not edit `versions/`, `receipts/` or the fixed executable by hand. Register with `connect claude-code` (preview) and `--apply` only when asked; it changes the user's Claude Code `settings.json` and MCP registration. The former `plugin-update`/`plugin-bootstrap` commands are retired and must keep returning `USE_REMNIFOLD_INSTALL`.

For installer changes, run `cargo xtask updater-test --binary <absolute-native-executable> --archive <absolute-platform-archive> --work-root <absolute-external-work-directory>`. Add `--previous-archive <absolute-old-native-archive>` to check older clients' state stays readable. Inspect `local-plugin-update-validation.json` in that work directory.

For a first strict-route installation (Setup needs none of this), use a trusted Rust source build or the signed Windows bootstrap `velopack/remnifold-bootstrap-<version>-x86_64-pc-windows-msvc.exe` with a strict version (1.0.32 or earlier). Verify its Authenticode signature (status `Valid`, signer CN `Open Source Developer Yuichiro Shinozaki`, RFC 3161 timestamp) before first execution and never execute an unverified R2 download. Unix uses `scripts/bootstrap-plugin.sh`. Follow [README.md](README.md#first-installation) and [DESIGN.md](DESIGN.md#release-installation); never send GitHub credentials to R2 or print raw logs or secrets.

## R2 publication and trust

- CI validation/build commands never invoke Node.js or JavaScript package managers (PATH guard). SHA-pinned allowlisted Actions (`dev/src/ci.rs`) may run on the runner's bundled Node, but never in `publish-r2`, a step with secrets, or a `release/*` run. The rest of this section describes strict publication, which ended with 1.0.32 and stays only for the existing releases. Archives are built, verified and privately staged only by the `release/*` run on native GitHub-hosted runners (no hand-built or local-input archives); only the publisher, after every CI job succeeds, writes immutable objects to public `remnifold-updates` (`https://remnifold-updates.kagayoi.com`), creates the status, and conditionally updates `releases/<version>/index.json`. The bucket's `velopack/` prefix (Setup feed, signed bootstrap) is written only by `release-velopack.yml` (gated as in [Setup installer (Velopack)](#setup-installer-velopack)), never touching `releases/`. GitHub witnesses prove verification/publication acceptance, not local builds.
- Keep each `native-package` leg on its native runner (`runs-on` per target, host asserted against `CI_TARGET`) running prepare, package, verify, updater-test and staging, and `publish-r2` on `ubuntu-latest`. Type checks and tests run in parallel in `windows-server-contracts`/`windows-native-contracts` (no Environment, read-only); publication waits because `publish-r2` needs every job. Keep run/attempt-scoped output and temp directories, except the fixed `$GITHUB_WORKSPACE/target` for `Swatinem/rust-cache` (saved on `main` only).
- GitHub Environments are the credential boundary: `r2-staging` selects `release/*` only (`main` pushes run in secret-free `validation` and never stage); `r2-release` selected `release/*` for strict publication and selects the version tags `v*.*.*` that start `release-velopack.yml`. Use selected-branch policies (`protected_branches: false`, `custom_branch_policies: true`), not `ref_protected`; this rejects PR distribution access (owner/write access stays trusted). Keep staging credentials private-only and publication bucket permissions minimal; only the publisher may write statuses.
- A commit-status URL does not prove GitHub generated the publication. Require exact repository/workflow/commit/push/release-branch/run-attempt identity and the latest successful CI's unique successful `publish-r2` job, whose bounded raw log has exactly one manifest record and four unique matching V2 asset records (release schema 2; historical schema 1 needs all five V1 records). Reject mixed-schema, partial, duplicate, mismatched, unknown-target or missing witnesses before installation. Schema-2 receipts keep separate publication and witness run identities; their schema is independent of release schema.
- Public object keys and hashes are immutable. Repeated publication must prove the accepted prior index from its logs and complete public bytes. Provisional failed/cancelled/timed-out publication recovery must verify candidate logs and the entire previous object root before ETag CAS; do not overwrite a successful accepted index. Test competing publishers and interrupted/retried writes through isolated fixtures.
- Job-log retention limits fresh fetches; missing witness logs fail closed. Existing receipts allow `--verify-only` without retained R2/CI objects, but GitHub release/source metadata stays required. Keep config-absent historical releases' GHA/schema-1 compatibility; malformed present R2 config or invalid R2 publication never downgrades to legacy artifacts.

Unix archives are built by the same `native-package` legs on their native runners, always in commit mode against the clean Git source; never upload checkout-mode packages. Main/PR runs build and verify the same way in the secret-free `validation` Environment but never stage. Unix runtime coverage is limited to package verification and updater-test (no Unix native/client tests).

## Setup installer (Velopack)

Packages: Velopack packId `RemnifoldApp` (`Remnifold` collides with the work folder `%LOCALAPPDATA%\remnifold`), Velopack CLI 1.2.161 and crate `velopack = "=1.2.161"`. The feed `https://remnifold-updates.kagayoi.com/velopack/` (`releases.<channel>.json`) is separate from the strict `releases/<version>/index.json`. Remnifold is a **multi-process app** (one stdio `mcp` per session, a short-lived `hook` per prompt), so Velopack's apply, which force-stops every other process in the install folder, must never run during the day. Preserve this design (`native/src/app_update.rs`, `native/src/app_update/`); per-platform behavior and rationale are in [DESIGN.md](DESIGN.md#setup-installer-velopack):

- `main()` runs `VelopackApp` before any argument parsing, for every subcommand, with startup auto-apply **off**. Install, updated and uninstall hooks always exit 0 and never block install/update/uninstall. Each CLI call in a hook is bounded to three seconds through `updater::process::run` (Velopack ends hooks after 15 or 30 seconds); outside hooks (`update-apply`, a no-argument launch, `mcp`) the bound is 30 seconds (`connect::set_cli_timeout`).
- All platforms record registration in `setup-registration.json` (`native/src/app_update/registration.rs`). A client whose registration did not finish in a hook is retried at the next logon `update-apply`, no-argument launch or `mcp` start; keep that retry, because a lost MCP entry means Claude Code never starts `mcp`.
- The Claude Code/Codex MCP entry named `remnifold` and Remnifold's own Claude Code hooks are Remnifold's: registration leaves an entry that already points at this executable untouched and replaces one that points at another Remnifold install (this is how a strict-`install` user migrates to Setup). The logon apply entry (`<packId> Update`, LaunchAgent, autostart file) never overwrites or removes one that points at another install. Uninstall and `connect <tool> --remove [--apply]` remove only entries pointing at their own executable.
- A background thread inside `mcp` (never hooks) checks and downloads, never applies. It writes nothing to stdout (diagnostics go to `app-update.log`); throttling and the exclusion lock are described in DESIGN.md. Non-Velopack builds (development, strict `install`) do nothing.
- `update-apply` (run at logon) exits immediately when nothing is pending, never applies while any other process runs from the install folder (no forced termination), verifies the signer first (Windows: Authenticode CN of every PE; macOS: Developer ID team `SL228Y8UUR` plus notarization; Linux: HTTPS, feed hashes, exactly one AppImage), then applies without restart.
- macOS and Linux have no Velopack hooks or uninstaller: a no-argument launch registers synchronously and the `mcp` update thread re-checks (as does the logon `update-apply`, on every platform), gated by `setup-registration.json` and a try-lock. On Linux the registered executable is the **AppImage file itself** (`$APPIMAGE`), never Velopack's per-launch mount path. `remnifold uninstall-setup --apply` is the uninstall step on both. The macOS LaunchAgent needs `AbandonProcessGroup` (see DESIGN.md).
- The `update-feed-test` Cargo feature (never in production builds) enables `REMNIFOLD_UPDATE_FEED_DIR` and `REMNIFOLD_UPDATE_ALLOW_UNSIGNED=1`. `scripts/velopack/pack-windows.ps1` builds without features and refuses `-Sign` with test options.

Validation without touching the real app: use a test packId (for example `RemnifoldVelopackTest`, never `RemnifoldApp`), `--installto` under an external work folder, and process-scoped `REMNIFOLD_HOME`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `TEMP`/`TMP` and a `PATH` whose first entry holds stub `claude`/`codex` executables that only record their arguments. Build the test executable with `--features update-feed-test`, pack unsigned versions with `scripts/velopack/pack-windows.ps1 -PackId <test id> -PackVersion <x.y.z> -Binary <exe>`, and remove the test HKCU `Run` value, Uninstall entry and install folder afterwards. On macOS (`ssh mac`), keep everything, including the toolchains, under one work folder, set `HOME` too, install from the Portable zip instead of the `.pkg`, pack with `scripts/velopack/pack-macos.sh <empty dir> --pack-id <test id> --version <x.y.z> --binary <exe>`, and run `vpk` with `--skip-updates`. A real `launchctl bootstrap` must use the test label and end with `bootout`; signing uses a temporary keychain, never the login keychain. On Linux, `velopack-linux.yml` (no Environment, secrets or R2) packs test versions and runs `e2e-linux.sh` under `$RUNNER_TEMP` with stub CLIs first on `PATH`. Registry unit tests use a private app hive (`RegLoadAppKeyW`).

Velopack packaging is PowerShell/Bash under `scripts/velopack/` (external `vpk` and Sigilune; no Node.js). Releases are packed by `scripts/velopack/pack-windows.ps1 -Sign`, `scripts/velopack/pack-macos.sh --sign` and `scripts/velopack/pack-linux.sh` (production packId `RemnifoldApp`) and published by `scripts/velopack/publish-r2.ps1` (immutable versioned objects, `releases.<channel>.json` last) through `.github/workflows/release-velopack.yml`. It starts on a push of a lightweight tag `v<x.y.z>` on a `main` commit (GitHub Releases are not created), and a manual dispatch with that tag as the ref (`gh workflow run release-velopack.yml --ref v<x.y.z>`) re-runs it. A secret-free `gate` first runs `scripts/velopack/wait-main-ci.sh`, which requires a lightweight tag in the exact `v<x.y.z>` form equal to `v<.codex-plugin/plugin.json version>` on a commit that is an ancestor of the default branch, then waits for that commit's `ci.yml` push run on the default branch to succeed (no `publish-r2` requirement) and re-checks the tag. Only then do four independent jobs run in `r2-release`, each first checking `cargo xtask ci-release-tag` and skipping a channel that already lists the version (failing when a newer version is listed): `windows-installer` (`win`, Certum through Sigilune), `macos-installer` (`osx`, `macos-latest`, Developer ID signing and notarization from a temporary keychain; the Apple secrets reach only the keychain step) and `linux-installer` (`linux-x64` on `ubuntu-24.04`, `linux-arm64` on `ubuntu-24.04-arm`, glibc 2.39 or lower). Running these scripts by hand is an external write needing an explicit request. The Windows pack extracts the signed `lib/app/remnifold.exe` as the bootstrap executable and verifies its Authenticode status, signer CN and timestamp; `publish-r2.ps1` places it as an immutable versioned object and refuses a version lower than the published feed's maximum (`-AllowOlderVersion` only for an intentional rollback). Never move signing into `ci.yml`, which builds and verifies every target and holds the strict publication witness of the existing releases.

## Dependency maintenance

- Update Rust manifests and the root `Cargo.lock` together and run locked checks. Keep the native crate's declared minimum Rust distinct from the development/CI toolchain (see [Validation](#validation)).
- Native tool versions, download URLs, and SRI values are pinned in `dev/`; update their manifest and integrity expectations together. Keep archive traversal, linked-path, cached-tool tampering, and digest checks effective. Do not weaken integrity checks or invoke a JavaScript package manager as a fallback.
- Keep `.github/dependabot.yml` covering Cargo workspace dependencies and SHA-pinned GitHub Actions weekly, with minor/patch updates separate from majors.

## Validation

Use Rust 1.100.0 for development and CI; preserve the native crate's declared Rust 1.97 minimum. Run commands from the repository root with the root workspace lockfile. The native toolchain downloads pinned esbuild, native TypeScript, workerd, and Cloudflare types without Node.js into `.devtools` (`--tool-root <absolute-cache>` overrides). `--work-root <absolute-output>` or `REMNIFOLD_VALIDATION_DIR` selects validation output (default `<OS-temp>/remnifold-validation`). Updater work roots must stay outside the repository, plugin source, and Codex home, with no linked ancestors; do not depend on machine-specific drives or folders.

```sh
cargo xtask prepare
cargo xtask type-check
cargo xtask native-test
cargo xtask server-test
cargo xtask client-test
cargo xtask check
git diff --check
```

Source `.mcp.json` launches Cargo with `cwd: "."` and `./native/Cargo.toml`; source hooks resolve the same manifest under `${PLUGIN_ROOT}` because their working directory belongs to the user task. Run `cargo xtask prepare` before source launches to make the pinned native bundler available. Platform packages replace Cargo registrations with native executable commands; Windows package hooks additionally use the fixed Git Bash `commandWindows` launcher described in [DESIGN.md](DESIGN.md#local-app-integration). `connect claude-code` registers the same events against the installed fixed executable. Preserve hook matchers, timeouts, asynchronous behavior, and status messages; installed users need no Cargo. Windows client E2Es must exercise the packaged Git Bash path for capture and recall, including Unicode/metacharacter paths, original stdin, and redacted failure/exit behavior.

`check` combines type checking, native tests, real-workerd server tests, native client E2Es, platform packaging/verification, and isolated updater tests, using local checkout verification internally (no release-commit claim, no publication). Inspect validation artifacts and failures before reporting success. No remote live test is part of ordinary checks; `remnifold server-live-test` targets the configured remote memory endpoint (explicit request only; `--keep` retains its test records).

Create a platform package with `cargo xtask package --target <Rust-target>` (optionally `--binary <absolute-prebuilt-executable>`, `--output <absolute-tar.gz-path>`, `--source-commit <sha>`). The default `--source-mode commit` requires an actual Git commit, clean source files with no untracked source, and matching Git blob identities; a supplied SHA alone does not prove that identity. Supported targets are `x86_64-pc-windows-msvc`, `aarch64-apple-darwin`, `x86_64-unknown-linux-gnu`, and `aarch64-unknown-linux-gnu`. Packages contain `remnifold/bin/remnifold` (Windows: `remnifold.exe`) and `native-build.json` binding target, source commit, version, and file digests. Verify with `cargo xtask verify --target <Rust-target> --binary <same-absolute-executable> --archive <absolute-archive>` from the packaging checkout, with the same source identity. For uncommitted changes or exported source used only for local checks, pass `--source-mode checkout` to both commands (and `--source-commit <sha>` when Git is unavailable); it reports release-commit identity as unverified and never establishes publication readiness. CI must verify the final archive in commit mode before publication. GitHub Releases are not created; publication is a separate operation started by a version tag (see [Setup installer (Velopack)](#setup-installer-velopack)).

For agent-run Windows validation, set process-scoped `REMNIFOLD_KEEP_TEST_STATE=1` before launching tests. Each invocation retains its new UUID directory for the parent agent to inspect and clean with Prunlet under the applicable Windows deletion rules; report the retained paths and wait for local Worker processes and file handles to close first. This is an agent execution policy, not a product dependency (users and CI keep portable cleanup of their own invocation state). Do not clean other invocations or shared caches.

### Contracts to retain in tests

- Native CLI/MCP/hook subprocess tests must exercise storage, search, forget, capture, recall, setup, import, and legacy-reader migration through authenticated fixtures. Preserve public tool schemas, structured/text replies, Unicode output, fixed redacted failure codes, bounded waits, receipt concurrency, deterministic v2 multipart identities, and acknowledged retry suppression.
- Claude Code transcript capture must keep Codex import Codex-only, classify rows by `type`, exclude thinking/tool/request-copy/sidechain/meta/foreign-session rows, keep earlier turns' capture keys stable when notifications append continuation turns, and preserve the shared v2 custom-ID scheme with `sm_source: "claude-code"`.
- Recall must cover independent topic/recent suppression, compaction recovery, revision selection, shared context budgets, `maxRecentTasks`, `recallScope` (default `session`: no recent-task request, and topic candidates limited by exact `sessionId` before revision selection and caps, failing closed without a session ID; `all` keeps the former cross-session behavior), structured/browser request projection, user-only continuation topics across large output and UTF-8 boundaries, mismatched/incomplete/oversized history rejection, and discovery bounds. Manual project/topic ranking and provenance before hydration caps must stay distinct from automatic recall. Recent-task grouping precedes pagination, excludes the current session/ineligible records, and uses normalized chronology with creation-date fallback.
- Recall reads that carry a deadline must stay bounded across processes: at most two in-flight via the `recall-locks` slots, at most three attempts for 429/502/503/504 inside the deadline, no waiting past it, fail-open with the existing notice (`native/tests/hook_concurrency.rs` uses a throttling fixture). Stop capture must not use these slots.
- The real native client must connect to the authenticated Worker in local workerd with migration-backed SQLite and deterministic AI/vector fixtures. Server tests must preserve atomic mutation, source/checkpoint consistency, FTS updates, scoped search/consolidation, stable ties, Unicode/embedded-NUL projections, and restore/forget cleanup races. Keep bounded startup/request waits and stop local Worker processes before cleaning SQLite state.
- Enrichment must preserve revision guards, project-scoped facts, stale topic/vector rejection, update/forget races, bounded Vectorize lookups, forgotten-vector cleanup with AI disabled, and late-upsert/deletion repair. Topic browsing must include unclassified records and exact-topic filtering across legacy and shared spaces. Topic re-enrichment preserves opt-outs and invalidates affected checkpoints; accepted jobs are not completion.
- Consolidation must retain truncated-output retry, publication races, stale checkpoint recovery, and redacted enrichment/scheduled failure diagnostics. Exclude recall opt-outs from target counts, new inputs and prior-checkpoint carry-forward, with publication-time guards and migration-backed invalidation of historical polluted checkpoints. Empty-query profiles must scope both facts and fallback memories to the requested source scope. Preserve both cron definitions in `server/wrangler.example.jsonc`; consolidation requires `0005_memory_consolidations.sql` and the opt-out repair in `0011_consolidation_recall_opt_out.sql`.
- Organization changes require authenticated native CLI/MCP client journeys and real-workerd fixtures. Preserve bounded prepare/lookup/source paging, owner-only REST authorization, lease/revision guards and idempotent commits, partition/recall eligibility, private multipart continuation until complete coverage, duplicate-capture deferral, source-edit/forget invalidation, and mode-dependent semantic visibility/vector recovery. Apply `0009_memory_organization.sql` before clients use organization; keep original IDs and bodies retrievable. Treat stored text as untrusted evidence; generation and finite run budgets belong to `skills/organize-memory/`, which runs only on user invocation (no scheduled registration; `skills/setup-remnifold/` only pauses legacy tasks), and neither belongs in the native transport or Worker. Ranged `prepare` (`days`) must not move the global discovery or fairness cursors and uses `0013_memory_created_index.sql` for its indexed scan.
- Current organization also requires `0010_capture_variants.sql` and `0012_organization_retry_fairness.sql`. Test exact body-hash verification and revision-bound coverage for distinct-key single-part v2 variants, conservative conflict deferral otherwise, guarded targeted HTTP retries, one-hour deferrals and bounded retry fairness across ordinary/multipart work. Capture counters never prove variant chronology. Preserve short authored summary recall in both native and server index reconstruction. Continuation-topic recovery must require a complete matching session header within its bounded header window and reject conflicting session metadata encountered during the backward scan.
- Session-filtered search (`sessionId`, `sessionIds`, `sessionUntil`, `sessionSource`) must return the same records with or without `0015_memory_search_projection_session.sql`; the index only affects speed. Keep the plan test in `server/tests/search-session.test.mjs` (index used after 0015, same rows before it) passing.
- Preserve the organization stdin contract in [README.md](README.md#memory-organization): bounded line/EOF input, Windows-only private console readiness before payload delivery, and redacted failures. Private-input changes must also verify echo/line-edit disabling, console restoration after a terminator, and failure handling in a dedicated Windows PTY; redirected-input rejection alone does not validate that path.
- Remote MCP/OAuth must preserve REST/client compatibility, additive migrations, transport validation, origin/consent checks, credential redaction, retry-safe saves, one-time concurrent code/refresh exchanges, revocation, owner-key rotation, registration limits, and failure without the OAuth migration. Authenticated provisioning verification must match exposed MCP tools.
- Authorization pages must retain same-origin consent referrers, `form-action 'self'`, HTTP 200 script-free completion with matching meta-refresh/fallback targets, no-store/no-referrer headers, consent-cookie clearing, escaped callback URLs preserving registered identity/state, and rejection of null/foreign consent origins or unsafe redirect hostnames. Validate decoded duplicate parameters and field lengths in both queries and forms.
- Provisioning tests must use Cloudflare REST fixtures rather than create resources. Cover read-only defaults, explicit `--apply`, preservation of configured IDs, bindings, cron schedules and routes, rejected conflicts, external resumable state, key redaction, skipped authenticated verification without a key, and recovery without replacement resources. Local tests do not establish that real remote provisioning or domain permissions work.
- Package tests must reject unsafe paths, wrong source identity/target/version, unexpected assets, changed tools, and mismatched executable bytes. Installer tests (the strict route) must preserve published-commit verification, receipt-based offline verification, immutable version folders, replacement of an open fixed executable, and readability of an older client's connection/capture state without touching the real app or configuration folders. For Windows hooks, retain acceptance of historical packages without overrides and rejection of partial, altered, or non-Windows overrides.

Validate bounded work by operation counts and returned-row sizes; do not run new-versus-old timing comparisons without explicit authorization.
