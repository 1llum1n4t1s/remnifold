# Repository guidance

This repository packages the Remnifold self-hosted Cloudflare server and its Codex plugin.

- Keep all local client and maintenance commands in `native/`, and development, build, packaging, and tests in the Rust workspace's `dev/` task runner. Windows, macOS, and Linux paths must run without Node.js, npm, pnpm, or Wrangler. Preserve existing public tool, HTTP, state, and capture-identity contracts.
- Keep the Worker TypeScript source in `server/`, bundled by native esbuild and deployed by the native `server-setup` command through Cloudflare REST. Production persistence stays in D1; the Durable Object SQLite adapter is test-only. Avoid dependencies unless they materially improve reliability.
- Preserve the storage, provenance, recall, and enrichment contracts in [DESIGN.md](DESIGN.md), including 1.x connection/environment readers, legacy capture receipts and spaces, existing document IDs, owner identities, and persisted `sm_*` metadata.
- Keep the official Codex local memory store outside this integration. Capture must retain deterministic keys/custom IDs, retry-safe document reuse, and redaction of the configured memory API key and supported secret patterns.
- Never commit API keys, generated resource IDs, `.dev.vars`, `.wrangler/`, or generated provisioning state. Metadata-only root/server `package.json` files support older version readers; they do not authorize restoring a JavaScript package-manager toolchain.
- Run the affected native, server, client contract, package, and updater checks below, plus `git diff --check`.
- Do not deploy, migrate a remote database, publish, create a remote repository, push, run `topics-setup --apply`, run `server-live-test`, or invoke remote consolidation without an explicit request. Local verification does not authorize remote changes.

## Standalone local plugin update

When explicitly requested, follow the packaged executable's `plugin-update` procedure in [README.md](README.md#connect-an-existing-server), including publication checking, explicit application, and verification with the same version and work root. Its external work-root and receipt-retention requirements also apply to agent execution. Validate the artifact against the release commit and use authenticated GitHub CLI and the official native Codex plugin CLI. Preserve connection and registration; do not edit the plugin cache directly. Report a required new chat or restart separately. Clean only invocation-specific temporary files under the applicable cleanup rules.

For updater changes, build the native platform archive and run `cargo xtask updater-test --binary <absolute-native-executable> --archive <absolute-platform-archive> --work-root <absolute-external-work-directory>`. Add `--legacy-archive <absolute-old-published-JavaScript-archive>` and `--previous-archive <absolute-old-native-archive>` to validate those migrations; do not rebuild an obsolete JavaScript package. Use the same work-root constraints as the actual updater. Native GitHub/Codex CLI fixtures isolate installation and failure scenarios from the real installation and remote memory. Inspect `local-plugin-update-validation.json` in that work directory for installation, preserved connection/capture state, idempotent retries, recovery after CLI failure, verification after CI artifacts expire, and rejection before installation changes for invalid publication inputs or local edits.

For a first Windows R2 download or migration from a pre-R2 updater, use the Rust `plugin-bootstrap` command from a trusted source build or the separately authenticated immutable GitHub Release bootstrap asset. Native GitHub CLI must be version 2.93.0 or newer before release-signature verification (CVE-2026-48501). `gh release verify` and `gh release verify-asset` must succeed before the first downloaded executable is run; an unverified R2 helper must never authenticate itself. The initial executable must remain in a trusted private directory between download, verification, and execution. The published bootstrap asset is the exact executable from the CI-verified Windows archive, bound to the release commit. Unix may use the trusted-source `scripts/bootstrap-plugin.sh`. Both routes independently authenticate the R2 archive through the exact GitHub publisher-log witness. Download-only must not invoke Codex or require an installed plugin; return the unchanged verified formal archive. Windows copies and rehashes it into a new private OS-profile `Remnifold/Downloads/<UUID>` directory, checking persistent ancestor ACLs and holding directory handles against rename. This formal delivery is separate from the external D: processing work root. Resolve physical existing path prefixes, including 8.3 names, and reject links, overlaps, unsafe ownership or ACLs without changing existing ACLs. Default publication checking is read-only; explicit apply migrates an existing registered installation and verifies its receipt. A fresh installation uses download-only and official plugin registration. Preserve legacy argument aliases where supported. Use native GitHub CLI and Rust; no Node/jq/Python/PowerShell/batch dependency or GitHub credentials at the public R2 origin. Unix ownership/mode and macOS strictly parsed deny-only ACL requirements remain. Bound stdout and stderr while reading. On Windows, assign suspended children to a kill-on-close Job Object before starting them and stop the full job tree on limit or timeout. Unix commands use an isolated process group, matching the trusted-source Bash bootstrap; intentionally daemonizing children that leave that group are outside that containment boundary. Publication checking and download-only create no installation receipt; successful apply retains its updater receipt. Retain invocation state until safe cleanup, and never print raw logs or secrets.

## R2 publication and trust

- CI and all five native build/test/package targets use no executable Actions or Node.js. Each target verifies clean Git source and its archive, then stages into private `remnifold-builds`; only the all-success publisher writes immutable archives/manifests to public `remnifold-updates` at `https://remnifold-updates.kagayoi.com`, creates the traceability status, and conditionally updates `releases/<version>/index.json`.
- GitHub Environments are the credential boundary: `r2-staging` selects `main` and `release/*`, `r2-release` selects `release/*`, and `validation` has no distribution secrets. Use selected-branch policies (`protected_branches: false`, `custom_branch_policies: true`), not `ref_protected`. This rejects PR distribution access without claiming global branch protection; repository-owner/write access remains trusted. Keep private-only staging credentials and minimum bucket-object permissions for publication; only the publisher has status-write permission.
- A commit-status URL does not prove GitHub generated the publication. Require exact repository/workflow/commit/push/release-branch/run-attempt identity and the latest successful CI's unique successful `publish-r2` job. Its bounded raw GitHub log must have exactly one manifest record and five unique matching asset records; reject partial, duplicate, mismatched, or missing witnesses before installation. Preserve separate publication and witness run identities in schema-2 receipts.
- Public object keys and hashes are immutable. Repeated publication must prove the accepted prior index from its logs and complete public bytes. Provisional failed/cancelled/timed-out publication recovery must verify candidate logs and the entire previous object root before ETag CAS; do not overwrite a successful accepted index. Test competing publishers and interrupted/retried writes through isolated fixtures.
- Job-log retention limits fresh fetches: missing witness logs fail closed. Existing receipts allow `--verify-only` without retained R2 or CI objects, while GitHub release/source metadata remains required. Keep config-absent historical releases' GHA/schema-1 compatibility; malformed present R2 config or invalid R2 publication must never downgrade to legacy artifacts.
- R2 publication is an external write and remains separate from local validation. Do not run staging, publishing, or live R2 smoke operations without an explicit request.

## Dependency maintenance

- Update Rust manifests and the root `Cargo.lock` together and run locked checks. Keep the native crate's declared minimum Rust version distinct from the current development/CI toolchain.
- Native tool versions, download URLs, and SRI values are pinned in `dev/`; update their manifest and integrity expectations together. Keep archive traversal, linked-path, cached-tool tampering, and digest checks effective. Do not weaken integrity checks or invoke a JavaScript package manager as a fallback.
- Keep `.github/dependabot.yml` covering Cargo workspace dependencies weekly, with minor/patch updates separate from majors. The workflow uses no executable Actions, so it has no GitHub Actions dependency entries. Metadata-only JavaScript manifests do not need npm dependency maintenance.
- Preserve the trust boundary in `.github/workflows/dependabot-auto-merge.yml`: execute only trusted default-branch workflow code, never PR code. Automatic merges require a same-repository Dependabot PR, allowed dependency-only changes, verified commits, successful latest CI for the exact head, passing remaining checks/statuses, and unchanged head/base with a mergeable PR immediately before merging. When required CI workflows change, keep `REQUIRED_WORKFLOWS` and the `workflow_run` trigger aligned; inspect the workflow summary for held PRs rather than bypassing its checks.

## Validation

Use Rust 1.99.1 for development and CI; preserve the native crate's declared Rust 1.97 minimum. Run commands from the repository root with the root workspace lockfile. The native toolchain downloads pinned esbuild, native TypeScript, workerd, and Cloudflare types without Node.js. The default cache is `.devtools`; `--tool-root <absolute-cache>` selects another location. `--work-root <absolute-output>` or `REMNIFOLD_VALIDATION_DIR` selects reproducible validation output. The default is `D:/Codex/remnifold/validation` on Windows and `<OS-temp>/remnifold-validation` on macOS/Linux. Updater work roots must stay outside the repository, plugin source, and Codex home, with no linked ancestors; on Windows use `D:/Codex/remnifold/...`.

```sh
cargo xtask prepare
cargo xtask type-check
cargo xtask native-test
cargo xtask server-test
cargo xtask client-test
cargo xtask check
git diff --check
```

Source `.mcp.json` launches Cargo with `cwd: "."` and `./native/Cargo.toml`; source hooks resolve the same manifest under `${PLUGIN_ROOT}` because their working directory belongs to the user task. Run `cargo xtask prepare` before source launches to make the pinned native bundler available. Platform packages replace Cargo registrations with native executable commands; Windows hooks additionally use the fixed Git Bash `commandWindows` launcher described in [DESIGN.md](DESIGN.md#plugin-integration). Preserve hook matchers, timeouts, asynchronous behavior, and status messages; installed users need no Cargo. Windows client E2Es require the [Git for Windows prerequisites](README.md#requirements) and must exercise the packaged Git Bash path for capture and recall, including Unicode/metacharacter paths, original stdin, and redacted failure/exit behavior.

`check` combines type checking, native tests, real-workerd server tests, native client E2Es, platform packaging/verification, and isolated updater tests. This uses local checkout verification internally, so uncommitted changes can be tested without claiming release-commit verification or publishing the test archive. Individual commands support focused iteration; inspect their validation artifacts and failures before reporting success. No remote live test is part of ordinary checks. `remnifold server-live-test` targets the configured remote memory endpoint and requires an explicit request; `--keep` retains its test records.

Create a platform package with `cargo xtask package --target <Rust-target>`, or add `--binary <absolute-prebuilt-executable>` for an already built target executable. Optional `--output <absolute-tar.gz-path>` selects the archive and `--source-commit <sha>` selects the source identity. The default `--source-mode commit` requires an actual Git commit, clean source files with no untracked source, and matching Git blob identities for the same source tree. A supplied SHA alone does not prove that identity. Supported targets are `x86_64-pc-windows-msvc`, `aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu`, and `aarch64-unknown-linux-gnu`. Packages contain `remnifold/bin/remnifold` (Windows: `remnifold.exe`) and `native-build.json` binding target, source commit, version, and file digests. Verify with `cargo xtask verify --target <Rust-target> --binary <same-absolute-executable> --archive <absolute-archive>` from the packaging checkout, with the same source identity. Both `package` and `verify` default to commit verification. For uncommitted changes or exported source used only for local checks, explicitly pass `--source-mode checkout` to both commands (and `--source-commit <sha>` when Git is unavailable). Checkout mode verifies the archive against local bytes and reports release-commit identity as unverified; do not use it to establish publication readiness. CI must verify the final archive in commit mode before publication. Release tagging and publication are separate operations.

For agent-run Windows validation, set process-scoped `REMNIFOLD_KEEP_TEST_STATE=1` before launching tests. Test invocations use new UUID directories and retain their state for the parent agent to inspect and clean with Prunlet under the applicable Windows deletion rules; report the retained paths and wait for local Worker processes and file handles to close before cleanup. This is an agent execution policy, not a product dependency: normal users and CI keep portable cleanup of their own invocation state and do not need a personal Prunlet installation. Retain only validation artifacts and state still needed for diagnosis or resumption; do not clean other invocations or shared caches.

### Contracts to retain in tests

- Native CLI/MCP/hook subprocess tests must exercise storage, search, forget, capture, recall, setup, import, and legacy-reader migration through authenticated fixtures. Preserve public tool schemas, structured/text replies, Unicode output, fixed redacted failure codes, bounded waits, receipt concurrency, deterministic v2 multipart identities, and acknowledged retry suppression.
- Recall must cover independent topic/recent suppression, compaction recovery, revision selection, shared context budgets, `maxRecentTasks`, structured/browser request projection, user-only continuation topics across large output and UTF-8 boundaries, mismatched/incomplete/oversized history rejection, and discovery bounds. Manual project/topic ranking and provenance before hydration caps must stay distinct from automatic recall. Recent-task grouping precedes pagination, excludes the current session/ineligible records, and uses normalized chronology with creation-date fallback.
- The real native client must connect to the authenticated Worker in local workerd with migration-backed SQLite and deterministic AI/vector fixtures. Server tests must preserve atomic mutation, source/checkpoint consistency, FTS updates, scoped search/consolidation, stable ties, Unicode/embedded-NUL projections, and restore/forget cleanup races. Keep bounded startup/request waits and stop local Worker processes before cleaning SQLite state.
- Enrichment must preserve revision guards, project-scoped facts, stale topic/vector rejection, update/forget races, bounded Vectorize lookups, forgotten-vector cleanup with AI disabled, and late-upsert/deletion repair. Topic browsing must include unclassified records and exact-topic filtering across legacy and shared spaces. Topic re-enrichment preserves opt-outs and invalidates affected checkpoints; accepted jobs are not completion.
- Consolidation must retain truncated-output retry, publication races, stale checkpoint recovery, and redacted enrichment/scheduled failure diagnostics. Preserve both cron definitions in `server/wrangler.example.jsonc` and apply `0005_memory_consolidations.sql` before installing a client depending on consolidation.
- Remote MCP/OAuth must preserve REST/client compatibility, additive migrations, transport validation, origin/consent checks, credential redaction, retry-safe saves, one-time concurrent code/refresh exchanges, revocation, owner-key rotation, registration limits, and failure without the OAuth migration. Authenticated provisioning verification must match exposed MCP tools.
- Authorization pages must retain same-origin consent referrers, `form-action 'self'`, HTTP 200 script-free completion with matching meta-refresh/fallback targets, no-store/no-referrer headers, consent-cookie clearing, escaped callback URLs preserving registered identity/state, and rejection of null/foreign consent origins or unsafe redirect hostnames. Validate decoded duplicate parameters and field lengths in both queries and forms.
- Provisioning tests must use Cloudflare REST fixtures rather than create resources. Cover read-only defaults, explicit `--apply`, preservation of configured IDs, bindings, cron schedules and routes, rejected conflicts, external resumable state, key redaction, skipped authenticated verification without a key, and recovery without replacement resources. Local tests do not establish that real remote provisioning or domain permissions work.
- Package tests must reject unsafe paths, wrong source identity/target/version, unexpected assets, changed tools, and mismatched executable bytes. Updater tests must preserve published-commit verification, receipt-based offline-artifact verification, official CLI installation, and legacy connection/capture-state preservation without changing the real plugin cache. For Windows hooks, retain acceptance of historical packages without overrides and rejection of partial, altered, or non-Windows overrides; prerequisite failures during `--apply` must precede installation changes.

Use operation counts and returned-row sizes to validate bounded work where appropriate; they do not measure deployed latency. Do not run new-versus-old timing comparisons without explicit authorization.
