# Setup Remnifold

Remnifold is a standalone app. Use its fixed executable: `%LOCALAPPDATA%\Programs\Remnifoldinemnifold.exe` on Windows, `~/Library/Application Support/Remnifold/app/bin/remnifold` on macOS, and `$XDG_DATA_HOME/remnifold/bin/remnifold` (default `~/.local/share/remnifold/bin/remnifold`) on Linux; `REMNIFOLD_HOME` moves it to `<REMNIFOLD_HOME>/app/bin`. If it is absent, this skill's own package root (its containing directory ascended two levels) also has `bin/remnifold`. Resolve absolute paths before running commands; the current task folder does not necessarily contain the executable.

For a request to stop a legacy organization schedule, preserve the existing connection and go directly to Memory organization below. Do not ask existing-server versus new-server setup questions or rerun connection setup. For an organization execution request, use organize-memory directly; it does not require another setup pass.

Determine whether the user is connecting to an existing server or creating resources in their own Cloudflare account.

Use the platform package matching the user's OS and CPU. MCP, hooks, connection and server setup, topic maintenance, status, history import, installation and updates use that one executable without Node.js, Cargo, Wrangler, Codex or a package manager.

For an existing server, obtain the HTTPS base URL without secrets in chat. Run the executable with `setup --base-url <HTTPS endpoint>`; accept the API key through its hidden prompt or process-scoped `REMNIFOLD_API_KEY`. `--api-key-stdin` supports noninteractive input without placing the key in arguments. `REMNIFOLD_API_URL` can provide the endpoint. The connection is written to the app's configuration folder (`%APPDATA%\Remnifold`, `~/Library/Application Support/Remnifold`, or `$XDG_CONFIG_HOME/remnifold`; `REMNIFOLD_HOME` or `--config-dir` overrides it); use `--force` when intentionally updating an existing connection and preserve its other settings. Setup verifies `/v3/session` before writing the connection. Run `status`, then the MCP `whoAmI` tool and report the discovered topic-search scope without printing credentials.

## Memory organization

Organization runs only when the user invokes it; it is no longer registered as a scheduled task. After connection setup and verification, mention that the user can organize memory on demand with the plugin's [organize-memory skill](../organize-memory/SKILL.md), for example "`$organize-memory 7`" or "organize the last 7 days of memory". The day count selects memories created in the last N days by server time, and an optional batch cap (default 3 for a ranged run) bounds one invocation. Ranged organization requires a server deployed with `0013_memory_created_index.sql` and the matching Worker; do not deploy or update the plugin for it without authorization.

Do not create, enable or change Codex automations, OS cron jobs or another scheduler for organization. For a request to stop or remove an organization schedule registered by an earlier version, discover the official Codex app `automation_update` capability and read its current schema, inspect the current Codex home's automations by name and prompt, and pause only a positively identified Remnifold organization task. A name alone is insufficient: preserve an ambiguous task and ask which one to change. Keep its notification preferences and unrelated fields, and never edit automation TOML directly. If official tools are unavailable, guide the user to Codex desktop Scheduled controls and report that the task has not been paused. Deleting a task is outside this skill unless the user asks for it through the official controls.

Separate invocation from readiness to run. A successful session check does not prove organization support; never use `prepare` as a readiness probe because it acquires a lease. An optional read-only `lookup --line` with a fresh harmless phrase can hint at endpoint compatibility, but success does not prove all migrations or publication behavior.

## Server and connection maintenance

For a new server, obtain a Cloudflare API token through process-scoped `CLOUDFLARE_API_TOKEN` or `--token-stdin` and run the executable's `server-setup --account-id <account-id>` for authenticated read-only discovery. No Wrangler OAuth credentials are imported. When deployment is authorized, supply the chosen memory key through `REMNIFOLD_API_KEY` and add `--apply`. The executable embeds the Worker bundle and migrations and uses Cloudflare REST to create or reuse D1 and Vectorize, apply migrations, deploy, and verify the endpoint. Consult `--help` for resource names and location. Account read, Workers scripts, D1, and Vectorize permissions are required; domains and routes require corresponding additional permissions. A request to prepare files locally does not authorize provisioning or deployment.

Use `--config <absolute-existing-jsonc-path>` to read existing installation settings without overwriting the input. Resume state defaults to `server/config.json` in the app's configuration folder (legacy state in the former Codex home is moved there only with `--apply`); `--state <absolute-json-path>` selects an external path outside the repository without linked ancestors. Preserve that state for updates and do not commit generated IDs or credentials. Existing bindings, cron schedules, and routes are retained; configuration conflicts must be resolved rather than replacing resources.

To update an existing server, inspect the read-only plan and select its existing Worker, D1 and Vectorize names; use the original explicit names if its configuration is unavailable. Preserve the existing key, configuration, D1 ID, memories and capture receipts. Apply server migrations and deploy before switching or updating clients. The additive OAuth migration does not require copying memories. Re-running the update resumes against the same resources. Supplying the existing key enables authenticated session and remote MCP tool-discovery verification; without it, report that those checks were skipped rather than claiming migration was verified. Never print the key.

For a remote MCP client, use the verified server base URL plus `/mcp` with Streamable HTTP. OAuth clients supporting public dynamic registration and PKCE can authorize on the server's consent page with the existing API key; compatible clients may instead use that key as a Bearer credential. OAuth tokens are MCP-only. Grok Bot's Connect apps and Grok custom connectors are documented by xAI, but manual Bearer entry in Grok Bot is unverified. For ChatGPT follow https://developers.openai.com/plugins/build/plugins: add a custom MCP server with URL and authentication, then create it as a private plugin. ChatGPT dots uses supported installed and enabled plugins; confirm that this plugin appears and works in the user's account rather than promising arbitrary URL entry. The server asks the AI to search, retrieve details and save durable context, but model tool calls are not guaranteed. Keep the local stdio server and hooks; do not add a duplicate remote registration in the same client.

Install or update the app only when the user asks. Run the fixed executable's `install --version <version>` to verify the publication, then `--apply` and `--verify-only` with the same version. Authenticated native GitHub CLI is required; Codex is not. The default work folder is `%LOCALAPPDATA%emnifold` on Windows and `~/.cache/remnifold` elsewhere; `--work-root <absolute-path>` must stay outside the app, configuration and repository folders without linked ancestors. Each version unpacks once into `versions/<version>` and is never overwritten with different bytes; the receipt in `receipts/` supports `--verify-only` after CI logs expire. Fresh installs require GitHub-generated publisher logs and fail closed after log retention. On Windows a running MCP server keeps the previous executable until restart; report `restartRequired` and any needed new session separately. The former `plugin-update` and `plugin-bootstrap` commands are retired and return `USE_REMNIFOLD_INSTALL`.

Register the installed app with `connect claude-code` (preview) and `connect claude-code --apply`: it registers the MCP server through `claude mcp add --scope user` (or prints the command when the CLI is not found; `--cli <path>` selects it) and merges the four hooks into Claude Code's `settings.json`, replacing only earlier Remnifold entries and keeping a one-time backup. `connect codex --apply` registers only the MCP server through `codex mcp add`; Codex has no supported way to register hooks outside plugins. Remove a former Codex plugin installation of Remnifold so that its hooks and MCP server are not duplicated. Start a new session after registering.

For a first installation, choose the bootstrap for the user's OS. On Windows, acquire the immutable GitHub Release asset `remnifold-bootstrap-x86_64-pc-windows-msvc.exe` with authenticated native GitHub CLI 2.93.0 or newer: successfully run `gh release verify <tag> --repo 1llum1n4t1s/remnifold`, download the asset into a trusted private directory, then successfully run `gh release verify-asset <tag> <absolute-downloaded-executable> --repo 1llum1n4t1s/remnifold` before executing it with `install --version <published-version> --apply`. Keep the binary in that private directory throughout. Follow the exact sequence in [README.md](../../README.md#first-installation). An unverified R2 helper must never authenticate itself. On macOS and Linux, obtain and review `scripts/bootstrap-plugin.sh` from trusted GitHub source, save it outside the work directory, and run it with Bash, native GitHub CLI, curl, tar, and `sha256sum` or `shasum`: `bash /absolute/trusted/bootstrap-plugin.sh --version <published-version> --apply` (without `--apply` it only verifies; `--download-only` returns the verified archive without running it). Never execute an unauthenticated download, send GitHub credentials to R2, or bypass a failed verification.

For an older installation, let the executable's `setup` command read `kagayoi-memory.json` or `supermemory.json` and legacy environment variables, then write the normal `remnifold.json` in the app's configuration folder without deleting the old files. A connection or state left in the former Codex home is migrated automatically on first use. Remove the former plugin to avoid duplicate hooks and MCP registrations. Do not rename or rewrite existing document IDs, physical spaces, deterministic capture IDs, or persisted `sm_*` metadata; those identifiers are compatibility contracts rather than current product branding. Remnifold is independent of hosted Supermemory.

Keep each installation isolated by endpoint and key. Save new records to the shared `memories` collection and preserve the derived project tag in `metadata.sm_project_id` as provenance. Existing folder spaces remain readable through global topic recall and browsing. Retrieve records through this integration's API; Codex's built-in local memory files remain outside this workflow.

For manual saves, use the current task's absolute `sourceFolder` or a single valid MCP workspace root when available to attach provenance. If the workspace is unavailable, save to the common collection without inventing a source folder. An explicit `containerTag` overrides storage. Browse with `listTopics` and `listDocuments` or `listMemories` using an optional `topic`; the default list spans all spaces. Use `topic: "__unclassified__"` for records awaiting classification, and `listSpaces` for physical storage diagnostics. `whoAmI` can report an unavailable workspace while API authentication and global discovery remain connected.

When updating to topic browsing, apply the server migrations and deploy the compatible backend within the user's authorization before updating the client. Existing records retain their IDs and physical spaces. Preview old-record classification with the executable's `topics-setup --limit 10`; when remote enrichment is authorized, add `--apply` to queue that finite batch. The default limit is 10 and valid limits are 1–50. This refreshes existing AI/vector/fact enrichment and invalidates affected project checkpoints while retaining opt-outs and revision guards. The command reports accepted jobs rather than completion. Verify classification through `getDocument` and `listTopics` before another batch. Classification uses the existing Workers AI enrichment call and billing; with enrichment disabled, records remain in the unclassified list.

For code changes, use the Rust workspace's `cargo xtask check` and `git diff --check`; the focused type, native, server, client, package, and updater commands are documented in [AGENTS.md](https://github.com/1llum1n4t1s/remnifold/blob/main/AGENTS.md). The combined check verifies local checkout bytes without establishing release-commit identity. Separate `package` and `verify` default to `--source-mode commit`; use explicit `--source-mode checkout` only for local uncommitted/exported-source validation, never as proof of publication readiness. Installed consumer packages need neither Cargo nor the development toolchain. If an older server requires space-by-space discovery, treat the 100-space fallback limit as incomplete; current global topic search avoids that listing cap.
