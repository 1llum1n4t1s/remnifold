# Setup Remnifold

Paths below are relative to the installed plugin root: start from this skill's containing directory and ascend two levels. Resolve them to absolute paths before running commands; the current task folder does not necessarily contain the plugin's executable.

For a request to stop a legacy organization schedule, preserve the existing connection and go directly to Memory organization below. Do not ask existing-server versus new-server setup questions or rerun connection setup. For an organization execution request, use organize-memory directly; it does not require another setup pass.

Determine whether the user is connecting to an existing server or creating resources in their own Cloudflare account.

Use the platform package matching the user's OS and CPU. Its local executable is `bin/remnifold.exe` on Windows and `bin/remnifold` on macOS and Linux; resolve that path from the plugin root. MCP, hooks, connection and server setup, topic maintenance, status, history import, and local plugin updates use that executable without Node.js, Cargo, Wrangler, or a package manager. The plugin manifest discovers this skill through `./skills/`.

For an existing server, obtain the HTTPS base URL without secrets in chat. Run the executable with `setup --base-url <HTTPS endpoint>`; accept the API key through its hidden prompt or process-scoped `REMNIFOLD_API_KEY`. `--api-key-stdin` supports noninteractive input without placing the key in arguments. `REMNIFOLD_API_URL` can provide the endpoint. Use `--codex-home` when needed and run Codex with the same home; use `--force` when intentionally updating an existing connection and preserve its other settings. Setup verifies `/v3/session` before writing the connection. Run `status`, then the MCP `whoAmI` tool and report the discovered topic-search scope without printing credentials.

## Memory organization

Organization runs only when the user invokes it; it is no longer registered as a scheduled task. After connection setup and verification, mention that the user can organize memory on demand with the plugin's [organize-memory skill](../organize-memory/SKILL.md), for example "`$organize-memory 7`" or "organize the last 7 days of memory". The day count selects memories created in the last N days by server time, and an optional batch cap (default 3 for a ranged run) bounds one invocation. Ranged organization requires a server deployed with `0013_memory_created_index.sql` and the matching Worker; do not deploy or update the plugin for it without authorization.

Do not create, enable or change Codex automations, OS cron jobs or another scheduler for organization. For a request to stop or remove an organization schedule registered by an earlier version, discover the official Codex app `automation_update` capability and read its current schema, inspect the current Codex home's automations by name and prompt, and pause only a positively identified Remnifold organization task. A name alone is insufficient: preserve an ambiguous task and ask which one to change. Keep its notification preferences and unrelated fields, and never edit automation TOML directly. If official tools are unavailable, guide the user to Codex desktop Scheduled controls and report that the task has not been paused. Deleting a task is outside this skill unless the user asks for it through the official controls.

Separate invocation from readiness to run. A successful session check does not prove organization support; never use `prepare` as a readiness probe because it acquires a lease. An optional read-only `lookup --line` with a fresh harmless phrase can hint at endpoint compatibility, but success does not prove all migrations or publication behavior.

## Server and connection maintenance

For a new server, obtain a Cloudflare API token through process-scoped `CLOUDFLARE_API_TOKEN` or `--token-stdin` and run the executable's `server-setup --account-id <account-id>` for authenticated read-only discovery. No Wrangler OAuth credentials are imported. When deployment is authorized, supply the chosen memory key through `REMNIFOLD_API_KEY` and add `--apply`. The executable embeds the Worker bundle and migrations and uses Cloudflare REST to create or reuse D1 and Vectorize, apply migrations, deploy, and verify the endpoint. Consult `--help` for resource names and location. Account read, Workers scripts, D1, and Vectorize permissions are required; domains and routes require corresponding additional permissions. A request to prepare files locally does not authorize provisioning or deployment.

Use `--config <absolute-existing-jsonc-path>` to read existing installation settings without overwriting the input. Resume state defaults to `<CODEX_HOME>/remnifold/server/config.json` (`~/.codex/remnifold/server/config.json` by default); `--state <absolute-json-path>` selects an external path outside the repository and plugin without linked ancestors. Preserve that state for updates and do not commit generated IDs or credentials. Existing bindings, cron schedules, and routes are retained; configuration conflicts must be resolved rather than replacing resources.

To update an existing server, inspect the read-only plan and select its existing Worker, D1 and Vectorize names; use the original explicit names if its configuration is unavailable. Preserve the existing key, configuration, D1 ID, memories and capture receipts. Apply server migrations and deploy before switching or updating clients. The additive OAuth migration does not require copying memories. Re-running the update resumes against the same resources. Supplying the existing key enables authenticated session and remote MCP tool-discovery verification; without it, report that those checks were skipped rather than claiming migration was verified. Never print the key.

For a remote MCP client, use the verified server base URL plus `/mcp` with Streamable HTTP. OAuth clients supporting public dynamic registration and PKCE can authorize on the server's consent page with the existing API key; compatible clients may instead use that key as a Bearer credential. OAuth tokens are MCP-only. Grok Bot's Connect apps and Grok custom connectors are documented by xAI, but manual Bearer entry in Grok Bot is unverified. For ChatGPT follow https://developers.openai.com/plugins/build/plugins: add a custom MCP server with URL and authentication, then create it as a private plugin. ChatGPT dots uses supported installed and enabled plugins; confirm that this plugin appears and works in the user's account rather than promising arbitrary URL entry. The server asks the AI to search, retrieve details and save durable context, but model tool calls are not guaranteed. Keep Codex's existing stdio server and hooks; do not add a duplicate remote registration.

Install or update `remnifold` using Codex's plugin-creator workflow and its personal marketplace. Do not duplicate its hooks in user hooks or register a second copy of its MCP server. Codex requires user review and trust of current plugin hook definitions; installing alone is insufficient. After installation or update, use a new task to load the skills and MCP tools. Preserve the existing connection file and v2 capture receipts when replacing an older manual integration.

For an explicitly requested local plugin update, use the executable's `plugin-update --version <version> --work-root <absolute-external-directory> --check-published`, then `--apply` and `--verify-only` with the same version and work root. Authenticated GitHub CLI and native Codex CLI are required. Keep the work root outside the repository, plugin source, and Codex home, without linked ancestors; on Windows use a directory under `D:/Claude/remnifold`. Preserve connection and registration and use the official plugin CLI rather than editing cache files. Retain the work root's schema-2 verification receipt for checks without retained R2 objects or CI logs; publication and witness run identities remain distinct. Fresh downloads require GitHub-generated publisher logs, not just the status URL, and fail closed after log retention. Config-absent historical releases retain GHA/schema-1 compatibility; present malformed R2 configuration must not downgrade to artifacts. Report any required new task or restart separately.

For an old executable that cannot discover R2, choose the bootstrap for the user's OS, with an external unlinked work directory. On Windows, use native `plugin-bootstrap` from a trusted Rust source build or acquire the immutable GitHub Release asset `remnifold-bootstrap-x86_64-pc-windows-msvc.exe`. For the release asset, require authenticated native GitHub CLI 2.93.0 or newer, successfully run `gh release verify <tag> --repo 1llum1n4t1s/remnifold`, download the asset into a trusted private directory, then successfully run `gh release verify-asset <tag> <absolute-downloaded-executable> --repo 1llum1n4t1s/remnifold` before executing that first binary. Keep the binary in that private directory throughout acquisition and execution; follow the exact acquisition sequence in [README.md](../../README.md#connect-an-existing-server). An unverified R2 helper must never authenticate itself. Run the verified executable with `plugin-bootstrap --version <published-version> --work-root D:/Claude/remnifold/bootstrap`. Legacy `-Version`, `-WorkRoot`, `-DownloadOnly`, and `-Apply` aliases remain supported by the native command.

On macOS and Linux, obtain and review `scripts/bootstrap-plugin.sh` from trusted GitHub source and save it outside the work directory. Run it with Bash, native GitHub CLI, curl, tar, and `sha256sum` or `shasum`: `bash /absolute/trusted/bootstrap-plugin.sh --version <published-version> --work-root /absolute/external/remnifold-bootstrap`. The Bash script is for supported Unix targets only; a trusted Rust source build is also an alternative.

On either platform, `--download-only` retrieves a GitHub-witness-verified archive for a first installation without Codex or executing its contents; use the official registration procedure in the README afterward. Default mode checks publication using the verified new executable without requiring an installed plugin or invoking Codex. The Unix script rejects default mode when the authenticated target release source lacks native bootstrap support; use `--download-only` or a trusted current native `plugin-bootstrap --version <older-published-version>` for those releases. Only explicit `--apply` migrates an existing registered installation and verifies its receipt. Never execute an unauthenticated download, send GitHub credentials to R2, or bypass a failed verification. The source bootstrap is not included as an installed runtime dependency.

For an older installation, let the executable's `setup` command read `kagayoi-memory.json` or `supermemory.json` and legacy environment variables, then write the normal `~/.codex/remnifold.json` configuration without deleting the old files. Disable the former plugin before enabling `remnifold` to avoid duplicate hooks and MCP registrations. Do not rename or rewrite existing document IDs, physical spaces, deterministic capture IDs, or persisted `sm_*` metadata; those identifiers are compatibility contracts rather than current product branding. Remnifold is independent of hosted Supermemory.

Keep each installation isolated by endpoint and key. Save new records to the shared `memories` collection and preserve the derived project tag in `metadata.sm_project_id` as provenance. Existing folder spaces remain readable through global topic recall and browsing. Retrieve records through this integration's API; Codex's built-in local memory files remain outside this workflow.

For manual saves, use the current task's absolute `sourceFolder` or a single valid MCP workspace root when available to attach provenance. If the workspace is unavailable, save to the common collection without inventing a source folder. An explicit `containerTag` overrides storage. Browse with `listTopics` and `listDocuments` or `listMemories` using an optional `topic`; the default list spans all spaces. Use `topic: "__unclassified__"` for records awaiting classification, and `listSpaces` for physical storage diagnostics. `whoAmI` can report an unavailable workspace while API authentication and global discovery remain connected.

When updating to topic browsing, apply the server migrations and deploy the compatible backend within the user's authorization before updating the client. Existing records retain their IDs and physical spaces. Preview old-record classification with the executable's `topics-setup --limit 10`; when remote enrichment is authorized, add `--apply` to queue that finite batch. The default limit is 10 and valid limits are 1–50. This refreshes existing AI/vector/fact enrichment and invalidates affected project checkpoints while retaining opt-outs and revision guards. The command reports accepted jobs rather than completion. Verify classification through `getDocument` and `listTopics` before another batch. Classification uses the existing Workers AI enrichment call and billing; with enrichment disabled, records remain in the unclassified list.

For code changes, use the Rust workspace's `cargo xtask check` and `git diff --check`; the focused type, native, server, client, package, and updater commands are documented in [AGENTS.md](https://github.com/1llum1n4t1s/remnifold/blob/main/AGENTS.md). The combined check verifies local checkout bytes without establishing release-commit identity. Separate `package` and `verify` default to `--source-mode commit`; use explicit `--source-mode checkout` only for local uncommitted/exported-source validation, never as proof of publication readiness. Installed consumer packages need neither Cargo nor the development toolchain. If an older server requires space-by-space discovery, treat the 100-space fallback limit as incomplete; current global topic search avoids that listing cap.
